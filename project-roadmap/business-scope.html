The business we are serving

Business statement · report 1.1–1.2

Small content teams need a reliable way to turn their own recordings into playable video. Separate upload, conversion and storage tools create repeated work and unclear failures.

FlickPond will provide a reusable workflow for authenticated upload, asynchronous processing, status, stored-source retry and owner-authorised playback. The web app supports individual uploads. The Publisher CLI supports folders of videos through the same published API.

Chosen demonstration setting: a course team prepares owned recording clips, while an independent trainer prepares individual tutorials. This is a concrete example within the approved audience, not a new product category.

Ownership rule: the authenticated uploading account owns the asset. Team names do not create shared accounts, organisational ownership or student permissions.

Publishing rule: “publish” means prepare and retrieve owner-accessible outputs. It does not mean public distribution, embedding in an LMS or sharing with a class.

Four people to keep the scope concrete

These are fictional planning personas, not interviewed customers. Their roles come from the proposals. We invented the names, doodles and example situations. The IDs below remain stable across later documents.

P-01 / Primary content owner

Maya

Course coordinator

Maya prepares recordings that her course team owns. She has a folder of clips ready for processing.

Goal
Submit the folder once, see each result, retry failures and check playback.

Friction
Separate upload and conversion tools require repeated manual work. A failed encode can interrupt the preparation task.

Uses
Publisher CLI, then browser review

Needs, success and scope boundary
  • One result per submitted file, including readable failures.
  • A retry that uses the stored source.
  • Owner-only status and output access.

Success: The batch reports every file. Successful outputs play. Failed jobs can be retried without another upload.

Boundary: Maya’s account owns her uploads. The demo does not model shared team ownership, student access or an LMS.

One journey with two client choices

  1. PrepareMaya selects a folder of owned clips. Arun selects one owned video.
  2. SubmitThe owner logs in and submits through the CLI or web app.
  3. TrackThe client shows a queued, processing, done or failed outcome.
  4. RecoverThe owner retries a failed job from its stored source.
  5. ReviewThe owner checks the playable output. No class publication or public sharing occurs.

Jules makes the API integration reusable. Sam supports the workflow through deployment, scaling and recovery. Neither persona adds an extra application.

The seven use cases and acceptance stories

These stories preserve the proposal’s UC identifiers. They define observable outcomes for the scope. They do not specify API paths, schemas or service internals.

UC-1Web app and CLI

Register, log in and upload an owned video

As a content owner, I want to submit a supported video so that I can prepare it for playback.

Actor: Maya / Arun. Jules integrates the API.
Precondition: The person owns the demonstration content. Registration or login establishes the caller.

Accepted when

  • A valid authenticated upload of at most 100 MiB records the caller as owner and starts asynchronous work.
  • The client receives a reference it can use to track the submitted item.
  • The platform rejects anonymous, unsupported and oversized uploads.

Evidence later: Owned upload result plus anonymous, invalid-type and oversized rejection cases.

P2 §2.3 and UC-1. P1 §4.1–4.2 supplies background.

UC-2Background platform workflow

Process video into playable outputs

As a content owner, I want compatible outputs without manually running a converter.

Actor: Platform, for Maya / Arun
Precondition: The platform accepted a valid source.

Accepted when

  • A successful job provides MP4 output.
  • Suitable sources produce best-effort HLS at the supported ladder heights. HLS failure can retain the MP4 fallback.
  • A processing failure leaves a visible failure state rather than an indefinite success claim.

Evidence later: Source and job reference, state history, MP4 playback and HLS/fallback evidence.

P2 UC-2, §3.3. P1 §4.3.

UC-3Web app and CLI

Track status and access playback

As an owner, I want to see the processing result and check the resulting video.

Actor: Maya / Arun as owner-viewers
Precondition: The caller owns the submitted item.

Accepted when

  • The owner can retrieve queued, processing, done or failed status.
  • The browser plays the completed output. The CLI reports status and provides authorised output access.
  • Another owner cannot retrieve that item’s status or playback access through the API.

Evidence later: Owner status, browser playback, CLI output and cross-owner rejection.

P2 UC-3, §2.3, §3.3.

UC-4Web app and CLI

Retry from the stored source

As an owner, I want to retry a failed encode without transferring the same video again.

Actor: Maya / Arun
Precondition: The caller owns a failed job and its source remains available.

Accepted when

  • An authorised retry uses the existing source. The browser must not upload its remembered file again.
  • Only a failed job is eligible. The platform rejects other states and other owners.
  • The retry has a visible result. Attempts must not create unintended duplicate outputs.

Evidence later: Failed-to-retry workflow, unchanged source, no re-upload, rejection cases and output check.

P2 §2.3, UC-4, §3.4. Current gap: frontend/app.js lines 410–412.

UC-5Publisher CLI

Bulk-publish a folder and report results

As a course coordinator, I want a batch command so that I avoid repeating the same web upload task.

Actor: Maya. Jules builds the integration.
Precondition: Maya has credentials and a folder of team-owned demonstration videos.

Accepted when

  • The CLI submits the folder through the published API and reports each file’s outcome.
  • Failures remain visible in the batch result. This planning choice prevents a single success message from hiding failed files.
  • The client uses no service-code imports and no database credentials.

Evidence later: CLI command, per-file results, dependency review and actual implementation effort.

P2 §1.3, UC-5, §3.3–3.4. Per-file failure visibility is the chosen business acceptance interpretation.

UC-6Operator-controlled worker scaling

Scale processing capacity independently

As an operator, I want to change worker capacity without changing the user-facing service.

Actor: Sam
Precondition: A fixed test backlog and enough host capacity are available.

Accepted when

  • Worker count changes from one to two to three without scaling or redeploying Media Management.
  • The planned comparison uses thirty identical 60-second 720p clips and two vCPU per worker.
  • Results record throughput, queue wait, processing time, failures, CPU and memory against the proposal targets.

Evidence later: Worker configurations, unchanged Media Management version and the scaling results.

P2 UC-6, §3.3–3.4.

UC-7Operator and deployment pipeline

Release Processing and demonstrate rollback

As an operator, I want a separate Processing release so that I can change it without releasing Media Management.

Actor: Sam
Precondition: A previous Processing image and a new candidate image exist.

Accepted when

  • The pipeline deploys the new version and runs an upload-to-playback smoke test.
  • The Media Management container and media_db migrations remain unchanged.
  • The release can return to the previous image. The initial release-plus-smoke target remains at most ten minutes.

Evidence later: Image references, release timing, smoke output, unchanged components and rollback result.

What this work includes and excludes

Included

  • Register, log in and upload owned videos of at most 100 MiB.
  • Process to MP4 with best-effort HLS.
  • Track status, access outputs and retry failed jobs from stored sources.
  • Use the web app and Publisher CLI, including folder submission.
  • Deliver the proposed service separation, data ownership, boundary security and AWS deployment.
  • Measure scaling, performance, recovery, reuse, security and independent release.

Excluded

  • Profiles, password reset, titles/tags, sharing modes and external-video features.
  • Search, discovery, moderation workflows and product analytics.
  • Crop/clip UI completion, thumbnails, 4K, and direct/resumable uploads above 100 MiB.
  • Kubernetes, autoscaling, multi-zone or multi-region failover.
  • Historical migration, malware scanning and full key rotation.
  • For the chosen scenario: no LMS, student portal, new classroom permissions or shared team ownership.

Operational metrics remain required evidence. They are different from product analytics. The business examples do not expand the approved implementation scope.
