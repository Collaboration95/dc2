How the current application works

  1. The user registers or logs in. The API creates a signed token in a secure cookie.
  2. The browser sends a video to the upload route. The API checks its type and size.
  3. The API stores the source in MinIO. It creates a job in PostgreSQL.
  4. The API places the job identifier in Redis through RQ.
  5. A worker claims the queued job. FFmpeg creates the processed output.
  6. The worker records success or failure in the same jobs table.
  7. The browser polls the API. The API checks ownership before returning status and playback access.

MinIO stores the media files. PostgreSQL stores users and jobs. Redis carries queued work.

HLS divides video into playlists and segments for adaptive playback. The current application also provides an MP4 fallback.

The HLS ladder supports up to 360p, 480p and 720p. The source height limits the available renditions.

HLS is best effort. A job can succeed with MP4 output even when HLS generation fails.

Why separate containers do not complete the proposal

The API, workers and recovery task run as separate processes. They still share database access and job code.

The jobs table contains a foreign key to the users table. Workers call the same repository functions that the API uses.

This structure supports asynchronous processing. It does not provide the separate data ownership that Team 17 promises.

The proposed Media Management service owns accounts, assets, upload checks and playback decisions. It serves both clients.

The proposed Processing service owns jobs, attempts, outputs, the queue, workers and recovery. It exposes a private API.

The services exchange identifiers and API messages. Each service controls its own database and migrations.

Both databases may run on one PostgreSQL server. Separate roles must prevent access to the other service’s database.

A separate runtime is a process boundary. A bounded context defines where a business model and its rules apply.

Why DDD comes before the final architecture

Domain-driven design uses business terms and rules to define models. It helps explain why a service owns particular responsibilities.

The proposal already identifies four candidates: Identity, Media, Processing and Delivery. It combines Identity, Media and Delivery into Media Management.

Processing has a separate lifecycle and different capacity needs. Its jobs can wait, run, succeed, fail and retry.

An aggregate groups data whose rules need one consistency boundary. The proposal identifies Asset and ProcessingJob as aggregate roots.

Define the business rules before finalising tables and endpoints. For example, only the asset owner can request processing.

Define the rule for a valid worker claim. Define what happens when the same submission arrives twice.

Then draw the contexts, aggregates and interactions. Use these models to check the proposed two-service boundary.

You do not need a new event broker to demonstrate DDD. The proposal selects REST submission and the existing RQ queue.

An architecture decision record explains a decision, its alternatives and its consequences. Preserve AD-01 through AD-08 from the proposal.

Which gaps need decisions before code

Retry behavior. The backend can retry a failed job from its stored source. The browser currently uploads the remembered file again.

UC-4 requires stored-source retry in both clients. Fix the browser behavior without expanding the editor scope.

CLI authentication. The existing dependency reads the session cookie. It does not accept a bearer token.

The proposal permits a cookie or bearer token for the CLI. Choose the method before defining its contract.

Storage access. Current workers use shared MinIO credentials. The proposal requires presigned source access and least-privilege boundaries.

Decide how workers obtain fresh source URLs after a long queue wait. Decide who grants output writes and signs playback links.

The proposal diagram says “presigned URLs only”. Its prose specifically describes source reads and output delivery. Resolve the output-write policy explicitly.

Owner identity. A service token identifies the calling service. It does not automatically prove that an asset belongs to the forwarded owner.

Processing must check the owner against its stored references. Specify how duplicate submissions handle a different owner or changed parameters.

Persistence. The current model lacks a separate Asset record and recorded attempts. Both concepts need explicit schema and transition rules.

Why recovery needs more than new settings

The recovery task currently fails processing jobs after a 30-minute lease. It checks old queued jobs after a 60-minute grace period.

The proposal requires worker recovery or visible failure within five minutes. It requires missing queue entries to return within two minutes.

The current defaults do not meet those timing targets. The recovery loop also adds time between checks.

A shorter lease can incorrectly fail a healthy encode. Define how the system distinguishes a slow worker from a dead worker.

Define an attempt identifier or another way to reject stale completion. Test retries while an older attempt still exists.

The current queue check asks whether the RQ job record exists. A queue entry can disappear while that record remains.

Include that case in the failure experiment. Do not assume the existing test proves every form of queue loss.

The proposal also requires a Processing outage experiment during upload. Define how Media Management retains and resubmits pending work.

The existing recovery task cannot scan Media Management’s new database directly. Specify a recovery responsibility inside the service that owns the data.

AD-04 permits an outbox only if experiments show that reconciliation is insufficient. Do not add one without a demonstrated need.

What the results must demonstrate

The historical cloud report records 660 ms p90 for completed-job reads at 50 users. It records 5.8-second p90 login latency.

These are inherited observations. They do not demonstrate the new service boundary or processing scalability.

The scaling experiment uses thirty identical 60-second 720p clips. Compare one, two and three workers, each capped at two vCPU.

The initial throughput targets are at least 1.6 times baseline for two workers and 2.1 times baseline for three workers.

Median queue wait must fall at each step. The target permits zero failed jobs.

Record job throughput, queue wait, processing time, failures, CPU and memory. Preserve each run’s configuration and raw timestamps.

The status test uses fifty concurrent users for three minutes. Its target is p90 at most 700 ms, with errors below one percent.

The login test uses twenty concurrent logins. Its separate target is p90 below two seconds.

Measure independent release within ten minutes. Record unchanged Media Management and media_db versions. Demonstrate rollback to the previous Processing image.

All specified security failures must be rejected. The release image must contain zero fixable HIGH or CRITICAL findings.

The CLI must use no service imports or database credentials. Record its size and actual effort against the two-person-day target.

Targets are not results. The proposal permits justified target revisions before final tests. Preserve the previous target and the reason for each change.
