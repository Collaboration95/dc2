4. THE SMALLEST RECOMMENDED SCOPE

Business problem:
Small content teams repeatedly implement secure video upload, processing and access.
A reusable platform lets another application use those capabilities through stable APIs.

Core workflow:
An authenticated owner uploads a video, requests processing, checks status and accesses the result.
The platform also handles invalid input and a failed processing attempt.

Platform participants:
- Seed: an owned video asset, linked to a processing job.
- Producers: content owners who submit videos through client applications.
- Consumers: authorised viewers who access processed videos through client applications.
- Integrators: developers who reuse the published APIs.

Proposed implementation:
- Retain FlickPond as the main application.
- Define Media Management and Processing as candidate domain boundaries.
- Extract Processing if domain analysis supports that boundary.
- Give each service exclusive ownership of its records and migrations.
- Use separate credentials to prevent direct access to another service's tables.
- Deploy the services separately and vary worker capacity independently.
- Add one small script that uploads a video and retrieves its processing result.
- Use one cloud demonstration environment and one repeatable test workload.

The worker belongs to Processing. It does not need another business-service boundary.
Separate databases can share one database server if credentials enforce ownership.
Existing authentication can remain with Media Management for this project.
Explain that choice rather than creating an identity service without a domain need.

The exact service split remains a design decision until the team completes DDD.
Keep the platform workflow, cloud deployment and required evidence as firm commitments.

5. HOW TO SHOW DDD

Domain-driven design (DDD) uses business concepts to define models and boundaries.
A bounded context defines where one domain model and its terms apply.
An aggregate groups records whose business rules need a consistency boundary.
A domain event records a meaningful business change.

Produce a compact domain model before committing to the service split:

- Define terms such as Asset, Owner, ProcessingJob and Output.
- Identify the responsibilities of Media Management and Processing.
- Define candidate aggregates and their business rules.
- Show how the contexts communicate through commands, APIs or relevant events.
- Compare the proposed boundaries with the inherited design.
- Explain why extraction helps ownership, independent change or separate scaling.

Example rules to check with the team:
Only an authorised owner can request processing of an asset.
A completed job refers to an available output.
A repeated submission cannot create unintended duplicate processing.

These are candidate rules, not checked behavior of the current system.
Do not invent events or implement event sourcing merely to show DDD terminology.
Use the model to justify the boundary and its contracts.

6. EVIDENCE TO COMMIT TO

Functional evidence:
Demonstrate upload, processing, status and authorised playback in FlickPond.
Demonstrate the small client's use of the same published APIs.

Scalability evidence:
Compare one worker with two workers using the same workload and recorded resources.
Measure completed jobs per minute, queue wait and errors.
Provide sufficient CPU capacity for the comparison.
Record the limiting resource. Do not promise twice the throughput without measurements.
Select a numeric acceptance target after a short baseline test.
State the measurement plan in the proposal before that test.

Recovery evidence:
Terminate a worker during processing.
Show recovery or an explicit failure within a defined time limit.
Check that retries do not produce conflicting job states or unintended duplicate outputs.
Document how committed jobs reach the queue after a temporary queue failure.
Choose a reliable mechanism. The assignment does not prescribe an outbox implementation.

Security evidence:
Test cross-owner access, unauthenticated requests and forged internal commands.
Keep storage private. Protect credentials and public transport.
Check input type and size. Record security findings and their treatment.

Automation evidence:
Demonstrate scripted build, tests, security checks and cloud deployment.
Record the deployed version and the smoke-test result.

Reuse and maintainability evidence:
Record the small client's implementation effort and the capabilities it reuses.
Show that it needs no access to service internals or databases.
Explain independent deployment and contract compatibility.
Do not claim a percentage effort saving without a defensible comparison.

Worker recovery does not prove survival of a cloud host or availability-zone failure.
Manual replica changes do not prove autoscaling.
Label each demonstrated capability accurately.

7. WHAT TO REMOVE FROM THE CURRENT DRAFT'S FIRM COMMITMENTS

Keep search, moderation and product analytics outside the implementation scope.
Operational metrics remain necessary evidence. They differ from product analytics.
Also exclude billing, multi-tenancy, live streaming and third-party downloads.

Defer these changes unless a core requirement needs them:
- Direct upload through signed object-store URLs.
- A new token algorithm and a complete key-rotation system.
- New HLS delivery mechanisms or a new media format.
- Migration of historical Project 1 data.
- Automated asset deletion across services.
- A full portal for the second client.
- Multi-region deployment and a Kubernetes cluster.

For the demonstration, prefer a fresh dataset if historical migration is unnecessary.
Retain existing working media formats when they meet the chosen use case.
Keep authentication and ownership checks mandatory across the service boundary.
Defer a custom outbox only if a simpler mechanism meets the stated recovery criteria.
Do not defer durable job tracking, bounded retries or visible failure states.

The current draft includes many of these mechanisms as firm promises.
They are team design choices, not explicit course requirements.
The latest email resolves the draft's two lecturer-confirmation questions.
Replace those questions with the approved position and its DDD condition.
Replace the generic presentation dates with Team 17's listed slot.
