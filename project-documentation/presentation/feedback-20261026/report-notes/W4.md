## Draft — Persistence Design

### Owned relational schemas and transaction scope

Media owns `media_db.public` at migration head `media_0008`; Processing owns `processing_db.public` at `processing_0007`. There are eleven application tables in each database. The provisioner supports separate or shared Aurora clusters; use the separate-cluster deployment baseline explicitly rather than inferring physical placement from a logical ER diagram. The bootstrap creates separate owner/migrator/runtime roles and limits each service's access to its own database. Framework Alembic bookkeeping is separate from the application-table count. These are migration-head schemas reconstructed statically, not a live Aurora catalog inspection. [Media migration head](https://github.com/Collaboration95/dc2/blob/76282d3/media/migrations/versions/0008_upload_cleanup_schedule.py#L10), [Processing migration head](https://github.com/Collaboration95/dc2/blob/76282d3/processing/migrations/versions/0007_launch_reservations.py#L11), [configurable topology](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L63-L78), [bootstrap](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/bootstrap.py#L171-L262).

The diagrams distinguish database-enforced relationships from identifiers carried across contexts. `upload_reservations.asset_id` is unique but has no FK to assets: a reservation can precede the Asset. `assets.source_asset_id` and `assets.processing_job_id` are plain nullable UUIDs. Processing owner/asset identifiers do not reference Media's database. `submission_guards.job_id` is nullable and not unique; its SQL cardinality must not be drawn as one-to-one. `jobs.current_attempt_id` references attempts with DEFERRABLE INITIALLY DEFERRED, but is not unique. SQL does not require that referenced Attempt to have the same job_id; `lock_pair` checks that relationship in code. `retry_requests.attempt_id` and `cleanup_intents.job_id` are both real FKs and must remain visible. [Media base DDL](https://github.com/Collaboration95/dc2/blob/76282d3/media/migrations/versions/0001_media.py#L26), [reservations](https://github.com/Collaboration95/dc2/blob/76282d3/media/migrations/versions/0004_direct_uploads.py#L23), [Processing base DDL](https://github.com/Collaboration95/dc2/blob/76282d3/processing/migrations/versions/0001_intake.py#L14), [retry and cleanup FKs](https://github.com/Collaboration95/dc2/blob/76282d3/processing/migrations/versions/0002_lifecycle.py#L33), [code membership fence](https://github.com/Collaboration95/dc2/blob/76282d3/processing/lifecycle.py#L28).

A received command commits its inbox identity, domain changes and newly staged work/result envelopes in one Processing transaction. A result commits the Media inbox and projection together. `delivery.sql.accept` inserts the message ID and canonical body hash, treats an exact replay as a no-op and rejects conflicting content under the same identity. `stage` does not commit independently; its caller owns the state-and-outbox transaction. Publishing claims a due outbox row, commits, sends outside the lock and fences the acknowledgement with a claim token. Lost replies may therefore duplicate delivery. Retained SQL records and repair permit replay; this is not exactly-once SQS transport or an unconditional promise that an outage can never lose data. [command transaction](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L232), [result transaction](https://github.com/Collaboration95/dc2/blob/76282d3/media/messaging.py#L16), [inbox/outbox implementation](https://github.com/Collaboration95/dc2/blob/76282d3/delivery/sql.py#L18), [relay](https://github.com/Collaboration95/dc2/blob/76282d3/delivery/sql.py#L58).

Claim, heartbeat and finish lock the Job and validate the current Attempt. Successful publication additionally requires the same lease token, a live lease and deadline against `clock_timestamp()` and valid output descriptors in the attempt namespace. Long-running network I/O and FFmpeg do not hold these SQL locks. `job_messaging.state_version` identifies newer snapshots; Media rejects conflicting equal versions, stale attempts and terminal-state regressions. These are application-enforced transition rules, not extra CHECK constraints in the migration DDL. [lease transitions](https://github.com/Collaboration95/dc2/blob/76282d3/processing/lifecycle.py#L136), [DB clock/fence](https://github.com/Collaboration95/dc2/blob/76282d3/processing/lifecycle.py#L24), [emission](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L102), [projection transitions](https://github.com/Collaboration95/dc2/blob/76282d3/media/projections.py#L36).

The physical schema retains legacy data alongside native V1 structures. `jobs.source_url` and `source_url_expires_at` are still required columns, but native V1 intake writes an empty URL and current database time; it stores the immutable source descriptor in JSONB. `retry_intents` remains for the legacy peer path; native Media retry stages a command instead. `launcher_control` and `launch_reservations` are migration-head tables whose use depends on enabling unattended launch. Their presence is not evidence that the feature is active in a running environment. [native intake values](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L281), [legacy retry](https://github.com/Collaboration95/dc2/blob/76282d3/legacy/media_peer/lifecycle.py#L156), [native retry](https://github.com/Collaboration95/dc2/blob/76282d3/media/services/v1_lifecycle.py#L50), [optional launcher migration](https://github.com/Collaboration95/dc2/blob/76282d3/processing/migrations/versions/0007_launch_reservations.py#L1).

Four application queues and four associated DLQs describe the configuration with ShortEncodes enabled; the baseline without it has three queue/DLQ pairs. | Store | Owner / producer → consumer | Held data and schema | Consistency / retention |
|---|---|---|---|
| Aurora media cluster, media_db | Media | Users; assets; upload/source pins; result projection; request/cleanup/orphan and message records | Local transactions; projection eventually follows Processing. No general hard purge. Template backup retention is one day, distinct from row retention. |
| Aurora processing cluster, processing_db | Processing | Jobs, attempts, retry/guard/cleanup, message records, state versions, task bindings, optional launcher records | Local transactions and DB-time fenced transitions. No general hard purge; one-day backup retention. |
| S3 SourceBucket | Media; bounded client POST → Media verification → Processing pinned read | Direct upload and copied edit-source bytes, with SQL descriptors and VersionId | Versioned/private; immutable accepted identity by exact pin; asynchronous version deletion and bounded rescans; no active-object age-expiry rule. |
| S3 OutputBucket | Processing writes/cleans; Media authorises playback | Attempt UUID namespace with primary and optional HLS | SQL-fenced publication; S3 writes themselves are not rolled into SQL transactions. Version cleanup is asynchronous; no active-object age-expiry rule. |
| ProcessingCommandsQueue / processing-commands + ProcessingCommandsDlq | Media → Processing | submit/retry/cancel Envelope | At-least-once, content-aware SQL inbox; retention 7 days / DLQ 14 days; redrive after 5 receives. |
| ProcessingWorkQueue / processing-work + ProcessingWorkDlq | Processing → finite worker | work Envelope | At-least-once with durable binding/lease checks; retention 7 / 14 days; SQL queued-work repair. |
| ProcessingShortWorkQueue / processing-work-short + ProcessingShortWorkDlq | Processing → short encoder | Same work Envelope | Optional ShortEncodes; retention 7 / 14 days; same identity model, longer visibility. |
| MediaResultsQueue / media-results + MediaResultsDlq | Processing → Media | result Envelope | At-least-once; inbox and monotonic projection applied together; retention 7 / 14 days. |
| S3 FrontendBucket | Platform deployment | index.html, hashed JS/CSS, vendor assets; build manifest | Versioned/private; index last; cache-control is not a retention policy. No general object-age expiry is configured. |
| SSM activity parameters | Media/Processing repair | String epochs at activity/.../touched and quiet | Optimisation hints; malformed/missing hints cause full SQL pass. No domain authority or general expiry declared. |
| SSM configuration parameters | Service-specific runtime/migrator | DSNs and Media JWT secret | Configuration credentials; never include values in report. Not a session or job store. |
| Secrets Manager | Aurora platform | Managed master password | Bootstrap credential; managed lifecycle, not application account state. |
| CloudWatch Logs | Functions/tasks | Log events | Diagnostic events, not recovery authority; declared retention 7 days. |
| Local JSON journals | Operator | Deployment/session/release state; deploy-journal.json | Outside product requests; operator-managed files; no central expiry declared. |

### SQS envelope and five message kinds

All ten fields are required keys, even when their value can be JSON null. The baseline emits and accepts version 1. Unknown top-level/source fields are dropped; payload semantics are checked by the consuming service. Queue producer authority is separate from data validation. [Envelope](https://github.com/Collaboration95/dc2/blob/76282d3/contracts/v1.py#L158-L218), [version rules](https://github.com/Collaboration95/dc2/blob/76282d3/contracts/v1.py#L20-L44), [lane enforcement](https://github.com/Collaboration95/dc2/blob/76282d3/delivery/sqs.py#L1).

```text
Envelope = {
  schema_version: integer = 1,
  message_id: UUID string,
  kind: "submit" | "retry" | "cancel" | "work" | "result",
  owner_id: UUID string,
  asset_id: UUID string,
  job_id: UUID string | null,
  attempt_id: UUID string | null,
  state_version: strict integer >= 0,
  source: Source | null,
  payload: JSON object
}
```

| Kind / lane | Producer shape and consumer rules |
|---|---|
| submit → processing-commands | Source required; payload `{operations:[Operation]}`. Normal finalize emits null job/attempt, version 0; Processing assigns its own Job ID. Public asset job identity is not assumed equal to internal Processing Job ID. |
| retry → processing-commands | Media emits stored source with empty payload; operations remain on durable Job. Envelope permits a null source for retry; consumer compares one when present. Consumer request identity is payload.request_id when supplied, otherwise message_id. |
| cancel → processing-commands | Media emits source null and empty payload; job/attempt can be null. A durable SubmissionGuard supports cancel-before-submit. |
| work → processing-work or processing-work-short | Job, Attempt and Source required; payload `{operations:[Operation]}`. Stable work identity is derived from attempt + state_version. Worker compares envelope to stored acceptance before S3 GET. Short lane changes execution admission, not schema. |
| result → media-results | Normal producer emits Job/Attempt/Source and payload `{status, outputs:[Output], error, attempt_number}`; status is queued/processing/done/failed/cancelled. Cancellation is derived from Job.deleted_at, not stored in jobs.status. Consumer applies its identity/transition/output checks. |

Sources: [Media submit](https://github.com/Collaboration95/dc2/blob/76282d3/media/messaging.py#L31), [Media lifecycle command](https://github.com/Collaboration95/dc2/blob/76282d3/media/services/v1_lifecycle.py#L17), [Processing command consumer](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L232), [work/result producer](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L78), [claim checks](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L325), [Media result checks](https://github.com/Collaboration95/dc2/blob/76282d3/media/projections.py#L69).

**Precise result exception:** a no-job cancellation acknowledgement has job_id, attempt_id and source all null, with payload exactly `{status:"cancelled", cancellation_confirmed:true, command_message_id:<UUID>}`. The producer sets state_version 0; Envelope itself only requires a nonnegative integer. Media matches command_message_id to its retained cancel outbox record before releasing source cleanup. DLQs retain the original body and do not introduce a sixth kind. Payload validation excludes credential/token/media-byte-like key names and HTTP(S) URL strings. [contract exception](https://github.com/Collaboration95/dc2/blob/76282d3/contracts/v1.py#L192-L212), [cancel producer](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L186), [acknowledgement match](https://github.com/Collaboration95/dc2/blob/76282d3/media/projections.py#L139), [payload validation](https://github.com/Collaboration95/dc2/blob/76282d3/contracts/v1.py#L132-L154).

### S3 namespaces and lifecycle

| Bucket role / key layout | Writer and reader | Identity / lifecycle |
|---|---|---|
| Source: `staging/{owner_id}/{reservation_id}/source` | Client via bounded POST; Media verifies; Processing downloads | Adopted in place. Finalized UploadReservation owns exact VersionId. Expired-grant scans delete other versions and preserve the adopted pin. |
| Source: `sources/{owner_id}/{asset_id}/source` | Media copies a completed parent's verified primary for a new edit Asset | asset_source_versions owns copied-source pin. StagedObject survives uncertain writes and is removed atomically at adoption. |
| Output: `jobs/{job_id}/attempts/{attempt_uuid}/primary.{mp4,mkv,mp3}` | Processing worker PUT; Media authorises read | UUID is Attempt.id, not attempt_number. Operation selection determines extension; default mp4. |
| Output: same prefix + `hls/master.m3u8`, `hls/v{n}/index.m3u8`, `hls/v{n}/seg%05d.ts` | Processing plain-upload pipeline; Media authorised HLS routes | Only empty operations generate HLS. Source height chooses ladder. Master uploads last; only master is retained in outputs list. HLS failure may leave primary available. |
| Frontend: `index.html`, `<stem>.<SHA256-prefix10>.<js/css>`, `vendor/...` | Deployment builder/uploader; CloudFront reader | Static hosting, not domain state. Manifest records key/content_type/cache_control/size/SHA-256/MD5. Index uploads last. |

Source version pins and output attempt namespaces solve different problems. Output descriptors do not carry an S3 output VersionId: the SQL finish fence determines whether an attempt's objects become visible through the authoritative Job/result. Processing cleanup enumerates versions under retired attempt prefixes. Media deletes source versions after its cancellation acknowledgement. A stale PUT can finish after a delete, so successful scans do not prove that no later version can appear; retained intents rescan until their defined retirement conditions. Active successful media has no general age-expiry rule. ## Proposed ADR — relational authority with document-friendly reads

**Target:** `32-physical.md` → Technology and Services; detailed cross-reference in `34-persistence-detailed.md` → Persistence Design. **Status:** proposed report text, awaiting coordinator adoption; no implementation or migration authorised. **Decision scope:** the current context-owned metadata workload; bytes remain in S3.

The MongoDB suggestion is credible. An owner-facing Asset with source metadata, operation arrays and output descriptors is naturally document-shaped. The current model already embeds these variable values as JSONB rather than normalising each descriptor into another table. The choice must therefore turn on access patterns, consistency rules and operational requirements, rather than on the fact that the product stores videos. [Asset JSONB](https://github.com/Collaboration95/dc2/blob/76282d3/media/models.py#L36-L66), [Job JSONB](https://github.com/Collaboration95/dc2/blob/76282d3/processing/models.py#L15), [local projection](https://github.com/Collaboration95/dc2/blob/76282d3/media/projection_models.py#L12).

| Access pattern | Current PostgreSQL mechanism | Plausible MongoDB / DynamoDB design | Guarantee / work to preserve |
|---|---|---|---|
| Get own Asset + projected result; ordered owner listing | Local Asset/projection read and owner filter, ordered paging | Mongo owner/asset document; DynamoDB owner partition and asset key with a listing index | Tombstone visibility, namespace checks, paging, version-conditional updates. This is the best initial document-read candidate. |
| Read source and output descriptor lists | JSONB embedded values; bytes in S3 | Embedded document or keyed-item attributes | Source VersionId/size/hash; output attempt namespace; no blob migration into metadata store. |
| Inbox dedupe; retry identity by owner/key | Unique insert plus content hash inside domain transaction | Mongo unique message/request index; DynamoDB conditional key insert, transactionally coupled to domain mutation | Same identity/different body conflict; retained replay history; no end-to-end dedupe from key lookup alone. |
| State transition + outbox append | Same local transaction, potentially multiple tables | Mongo bounded embedded pending events or multi-document transaction; DynamoDB item transaction or explicit Streams/CDC outbox | No committed state without recoverable publication intent; duplicates and consumer ordering still handled. |
| Claim / heartbeat / finish | Job lock, current-attempt check, token and database-clock deadline | Conditional writes/CAS plus atomic aggregate/binding transitions | Current Attempt, token, lease/deadline and one-task binding. Define replacement clock policy; do not silently substitute client time. |
| Email, asset/job, retry/attempt/task-name uniqueness | SQL unique constraints, including composite keys | Mongo suitable unique indexes; DynamoDB identity/sentinel items and atomic reservations | Equivalent race-safe uniqueness, delete/tombstone lifecycle and owner scope. |
| Due outbox/cleanup scans; launcher capacity | Explicit due/partial indexes; locked claims; singleton gate | Due-time index/partition strategy, conditional work claims, explicit capacity gate or scheduler redesign | Avoid hot partitions; handle conflicts, retries and capacity releases/reconciliation. |

Current-code basis: [owner query and local join](https://github.com/Collaboration95/dc2/blob/76282d3/media/repositories/assets.py#L81), [version fence](https://github.com/Collaboration95/dc2/blob/76282d3/media/projections.py#L36), [dedupe/outbox](https://github.com/Collaboration95/dc2/blob/76282d3/delivery/sql.py#L18), [claim/finish clock and lock](https://github.com/Collaboration95/dc2/blob/76282d3/processing/lifecycle.py#L24), [binding checks](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L325), [uniqueness DDL](https://github.com/Collaboration95/dc2/blob/76282d3/processing/migrations/versions/0005_task_binding.py#L13), [partial cleanup indexes](https://github.com/Collaboration95/dc2/blob/76282d3/processing/migrations/versions/0006_cleanup_retirement.py#L23-L29), [launcher capacity](https://github.com/Collaboration95/dc2/blob/76282d3/processing/launcher.py#L238), [launcher send gate](https://github.com/Collaboration95/dc2/blob/76282d3/processing/launcher.py#L337).

MongoDB supports atomic single-document writes and multi-document ACID transactions on replica sets and sharded clusters; standalone servers do not support those transactions. Multi-document transactions have different cost and operational considerations from single-document writes. DynamoDB supports conditional actions in all-or-nothing transactions, currently up to 100 actions on distinct items and 4 MB in one account/Region. Conditions can accompany Put/Update/Delete actions; a separate ConditionCheck and Update cannot target the same item in one transaction. These alternatives can implement the required guarantees. Neither makes an arbitrary SQL/document/item write and an external SQS send atomic without a publication design. Mongo unique indexes can enforce relevant identities; on a sharded collection, eligible unique indexes must include the shard key as a prefix (and _id alone is not globally enforced when it is not the shard key). DynamoDB secondary indexes permit duplicate key values, so a design must reserve secondary identities explicitly with conditional writes and transactions. [MongoDB transactions — R5 N4](https://www.mongodb.com/docs/manual/core/transactions/), [MongoDB production considerations — R5 N5](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/), [MongoDB compound unique indexes](https://www.mongodb.com/docs/manual/core/index-unique/create-compound/), [DynamoDB transactions](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html), [TransactWriteItems API limits](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html), [conditional writes](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html), [Mongo unique-index restrictions](https://www.mongodb.com/docs/manual/core/index-unique/), [DynamoDB GSI key uniqueness](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/GSI.html), [AWS outbox — R5 M5](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

**Decision:** retain each context's PostgreSQL authority for this release. Atomic state/inbox/outbox transitions, database-enforced uniqueness, DB-time fenced leases and recovery queries are already implemented together. A wholesale replacement would require explicit redesign and regression evidence for these mechanisms. JSONB retains the document-friendly parts without adding another operational store. This is an implementation-based recommendation, not a claim that SQL always performs better or costs less. Aurora connection/capacity management, cold-resume latency and idle cost remain trade-offs to measure. [transaction implementation](https://github.com/Collaboration95/dc2/blob/76282d3/delivery/sql.py#L18), [DB-time lifecycle](https://github.com/Collaboration95/dc2/blob/76282d3/processing/lifecycle.py#L136), [bounded connection pool](https://github.com/Collaboration95/dc2/blob/76282d3/runtime_support/lambda_db.py#L1), [Aurora scaling configuration](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L501).

**When to revisit:** measure owner-list/read traffic, read latency, payload size, access-pattern stability and the cost of the current service-owned databases. Trial an owner/asset read projection only when an explicit requirement justifies it. Compare MongoDB and DynamoDB against keeping JSONB in Aurora, including migration effort, indexes/partitions, connection/capacity and conflict costs, extra operations, failure recovery and deletion/reconciliation. Preserve conditional state_version/attempt fences and tombstones before rollout. The current result contract supplies updates but is not a retained event log: a rebuild must also obtain a complete authoritative snapshot/backfill and reconcile missing/expired messages. No cost numbers or performance claims are asserted without measurements. [current snapshot producer](https://github.com/Collaboration95/dc2/blob/76282d3/processing/messaging.py#L78), [retention](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L596), [AWS database selection — R5 N1](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/db-selection.html), [DynamoDB modelling — R5 N2](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/data-modeling-foundations.html).

**Possible future CDC variant, not built:** committed DynamoDB item → stream → Lambda relay → queue/consumer, with idempotency, partial-batch retry and reconciliation explicitly designed. It must not be added to an as-built diagram. [AWS outbox — R5 M5](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), [Lambda with DynamoDB — R5 N6](https://docs.aws.amazon.com/lambda/latest/dg/with-ddb.html).

### Reconstruction / ORM cross-check

All 22 tables match the ORM in column names, storage types, nullability and primary/foreign/unique/check constraints. PostgreSQL migration DDL makes launcher_control.id SERIAL (an INTEGER plus a sequence default); the ORM Python default of 1 suppresses SERIAL when creating tables from models. The dictionary records the migration DDL. Two migration-defined recovery indexes are also absent from ORM metadata. These three representation differences do not establish live schema drift. This documentation does not alter the model. See [migration](https://github.com/Collaboration95/dc2/blob/76282d3/processing/migrations/versions/0007_launch_reservations.py#L18-L28), [ORM default](https://github.com/Collaboration95/dc2/blob/76282d3/processing/launcher_models.py#L21-L29) and [PostgreSQL SERIAL semantics](https://www.postgresql.org/docs/16/datatype-numeric.html#DATATYPE-SERIAL).

- `processing.attempts: migration indexes [('ix_attempts_recovery', ('state', 'next_dispatch_at'), 'None')]; ORM indexes []`
- `processing.cleanup_intents: migration indexes [('ix_cleanup_intents_due', ('next_try_at', 'attempt_id'), 'retired_at IS NULL')]; ORM indexes []`
- `processing.launcher_control.id: migration physical default nextval('launcher_control_id_seq'::regclass); ORM-created SQL default None (ORM Python default 1)`

Alembic framework bookkeeping (`alembic_version`) is excluded from the 22 application tables: its DDL is not declared by application upgrades. No live catalog was inspected.
