### Draft subsection: Public request and identity boundary

The normal API path is Browser/Publisher → CloudFront `/api/*` → API Gateway **HTTP API** → the selected MediaApi or ProcessingApi `live` alias. The two integrations are AWS_PROXY payload v2, with a 29,000 ms integration timeout. CloudFront's API behavior disables caching; static frontend files use the separate S3 OAC origin. CloudFront is the normal same-origin entry, but the public execute-api endpoint is not disabled or origin-restricted in this stack. Direct calls still use the same Gateway authorization. [HTTP API/integrations](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L1500), [CloudFront](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L1642), [AWS managed cache policy IDs](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-cache-policies.html), [AWS managed origin-request policy IDs](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/using-managed-origin-request-policies.html).

GatewayAuthorizer is a Media-owned **Lambda REQUEST authorizer**, not a managed JWT authorizer. Protected routes attach this hook; the five public route exceptions bypass it. Gateway invokes MediaAuthorizerAlias with payload v2, identity source `$request.header.Cookie`, simple Boolean responses and result-cache TTL **0**. A protected request missing the Cookie identity source is rejected by Gateway before invoking the authorizer ([AWS identity-source semantics](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-lambda-authorizer.html#http-api-lambda-authorizer.identity-sources)). When invoked, authorize calls session_token, which requires exactly one v2 cookie-list entry parsed with an `access_token` value. SimpleCookie collapses repeated names within one entry; do not describe this as strict rejection of raw duplicate cookie names. read_token verifies HS256 with Media's secret, requires `sub`, `exp`, `iat`, and parses the subject as UUID. authorize then looks up the current Media User row. Missing users, unsupported roles and exceptions deny. Both current roles `user` and `operator` become contract role `publisher`; operator permission is checked separately in the Media API. Success returns `isAuthorized=true` plus Actor context: `schema_version=1`, `integration=dc2-gateway-v1`, `owner_id`, `role=publisher`. [Gateway hook](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L1529-L1543), [cookie/user/role validation](https://github.com/Collaboration95/dc2/blob/76282d3/media/authorizer.py#L13-L60), [HS256 claims](https://github.com/Collaboration95/dc2/blob/76282d3/media/services/security.py#L48-L58), [Actor serialization](https://github.com/Collaboration95/dc2/blob/76282d3/contracts/v1.py#L66-L98).

Gateway invokes the selected API separately, with cookies and `requestContext.authorizer.lambda`. GatewayAdapter validates Actor, strips client `x-owner-id` and `x-role`, and injects `request.state.actor`. Media also revalidates the cookie and current User and compares them to Actor; admin endpoints additionally require current DB role `operator`. Processing trusts the injected Actor; retry/cancel require `publisher`. Processing does not hold Media's JWT secret or query its users table in its handler, but each protected Processing request with a valid token still has the synchronous Media authorizer lookup dependency. Replace the blanket claim “every interaction is SQS” with a qualification: **business commands/results cross asynchronously; edge authorization is a synchronous Media-owned dependency.** [GatewayAdapter](https://github.com/Collaboration95/dc2/blob/76282d3/contracts/gateway.py#L33-L104), [Media revalidation/admin](https://github.com/Collaboration95/dc2/blob/76282d3/media/api/deps.py#L16), [Processing identity](https://github.com/Collaboration95/dc2/blob/76282d3/processing/auth.py#L6), [secret scope](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L1196).

The only public authorization exceptions are `GET /api/media/health`, `GET /api/processing/health`, and `POST /api/media/auth/{register,login,logout}`. They bypass the authorizer. Health reports version/status, not DB readiness; IAM operator `ready` is not a public Gateway route. Nine Gateway route resources implement two protected ANY proxy/root pairs plus these five exceptions; the adapter returns 404 for exact service roots. Application operations are more numerous because proxy paths are dispatched within FastAPI. [Gateway routes](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L1602-L1621), [adapter public paths/root](https://github.com/Collaboration95/dc2/blob/76282d3/contracts/gateway.py#L40-L58), [operator ready](https://github.com/Collaboration95/dc2/blob/76282d3/contracts/gateway.py#L170).

### Draft subsection: Load distribution and the ALB decision

The generated application stack has no ALB/NLB, target group, listener, VPC Link, ECS Service or RDS Proxy. API Gateway invokes Lambda aliases directly; finite encoders have no HTTP listener/port mapping or inbound SG rule. Adding an ALB would not distribute these existing pull-based jobs. The implementation separates HTTP admission, queue buffering, consumer execution, launcher capacity and SQL capacity. This conclusion is a source-based design explanation, not an assertion about unrelated resources in the AWS account. [Template builder](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L208), [direct integrations](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L1560-L1586), [worker definition](https://github.com/Collaboration95/dc2/blob/76282d3/scripts/aws/v1/definitions.py#L1867).

|---|---|---|

| HTTP | Gateway routes and default open-stage throttle 20/s, burst 50; Lambda concurrent invocations | 29 s integration; account concurrency still shared; no reserved/provisioned concurrency configured |

Publication labelled `processing-work` calls `WakeOnWork.send` and asynchronously invokes ProcessingLauncher only after its SQS send succeeds; a minute EventBridge tick is the recovery net. `launcher.tick` observes SQL queued current Attempts, approximate visible standard-queue depth and ECS worker tasks, then `_reserve` serializes `launcher_control`. Let `demand=min(SQL backlog,visible)`, `occupied=live tasks+unexplained reservations`, `idle=occupied-bound workers`. SQL backlog counts all queued current Attempts, without a lane filter; standard-queue visibility constrains demand ([backlog query](https://github.com/Collaboration95/dc2/blob/76282d3/processing/launcher.py#L161-L169)). **Current review comparison: ALB + ECS HTTP service is not selected for this workload.** Such a topology would provide health-checked inbound HTTP tasks and sustained container resource control. It would add standing load-balancer infrastructure and ECS service operations, while queue workers would still need their own backlog/capacity policy. The current Lambda-integrated API and finite queue workers support idle compute reduction at the cost of cold starts, startup delay and explicit launcher logic. Reconsider the alternative if an inbound HTTP container fleet or sustained warm capacity becomes a demonstrated need. This is the report's explicit alternative analysis. It is not a recovered historical ALB rejection, an implemented topology or a comparative benchmark. The earlier decision register rejects always-on ECS workers; do not fabricate an earlier ALB experiment. [Existing finite-worker decision](https://github.com/Collaboration95/dc2/blob/76282d3/docs/architecture/decisions.md#L158), [AWS ECS service load balancing, R5 L7](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-load-balancing.html).

Explain the pattern separately from the AWS implementation: [Queue-Based Load Leveling, R5 L3](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling) supplies the buffering rationale; [Competing Consumers, R5 L4](https://learn.microsoft.com/en-us/azure/architecture/patterns/competing-consumers) describes multiple retrieving workers. Neither proves the capacity or performance of this deployment. They justify naming the mechanisms rather than calling SQS an HTTP load balancer.
