### Continuous Delivery: correct the source / artifact and restore claims

> Automatic CD admission binds the triggering successful Main push CI run/attempt to the source SHA. A manual deploy/release may instead use a successful exact-source full CI dispatch; scheduled CI and PR runs are ineligible. [Admission validation][cd-gate-validation], [manual selection and automatic provenance][cd-gate-selection]. CD checks out that SHA and verifies the images it actually promotes using config-ID/source evidence, immutable registry digests and completed ECR scans. A successful source CI run alone does not prove reuse of the identical image bytes built in CI. Owner promotion uses a public smoke and attempts automatic restore on failure, recording restored/abandoned/restore-failed outcomes as appropriate. A candidate that provably changed nothing can be abandoned. The separate upload-to-playback smoke follows promotion and fails CD on error; it does not independently promise alias restore. [Exact checkout and execution][cd-checkout], [scan identity modes][scan-modes], [release proof][release-proof], [restore handling][restore], [later smoke][cd-smoke].
>
> Candidates and companion images that remain running stay subject to strict image policy. An image being replaced can be retained solely as the restore target with recorded fixable **Trivy** findings (`RETAINED_FIXABLE`). This does not waive ECR validation: all image sets still require a completed scan for the correct digest with no unaccepted HIGH/CRITICAL findings. Scan identity/completeness failures still block. [ECR policy][ecr-policy]. The exception permits remediation of a vulnerable baseline and does not waive the policy for newly promoted or kept-running images. ### Security / Scope limits: add “What the local DAST stage tests”

> The DAST target is a disposable HTTPS loopback gateway bridge invoking V1 Media/Processing handlers and the Media authorizer, backed by real PostgreSQL and run-scoped Moto S3/SQS. It is not deployed API Gateway or a scan of the AWS edge. The harness regenerates both OpenAPI schemas and rejects stale schemas or an unreviewed operation-count change. Out of the 15 Media and 5 Processing operations, it imports the seven selected GET routes below. [Target boundary][dast-target], [schema generation and selection][dast-schema].

| Service | Imported ZAP operation |
|---|---|
| Media | `GET /api/media/auth/me` |
| Media | `GET /api/media/health` |
| Media | `GET /api/media/jobs` |
| Media | `GET /api/media/jobs/{job_id}` |
| Processing | `GET /api/processing/health` |
| Processing | `GET /api/processing/jobs` |
| Processing | `GET /api/processing/jobs/{job_id}` |

Route source: [Media schema][media-schema] and [Processing schema][processing-schema], filtered by [reviewed exclusions][dast-exclusions].

> The scanner invokes `zap-api-scan.py` against private OpenAPI subsets with the pinned ZAP container and API-Minimal policy. It uses active API scanning rather than a baseline-only command. It seeds two synthetic owners and uploads, checks valid owner reads, denies cross-owner reads/deletes and forged owner headers, and rejects missing/expired sessions. The active scanner uses one valid owner's cookie, restricted to the local `/api/media` and `/api/processing` origin. Direct fixture checks are separate evidence and do not expand the scanner's seven-route coverage claim. [Scanner invocation][zap-invoke], [authentication fixtures][dast-auth], [cookie scoping][dast-cookie].
>
> Auth lifecycle POST operations, upload grants/adoption, HLS routes with signed storage URLs, operator/admin routes and other state-changing operations are excluded from active scanning. During scanning the gateway rejects excluded or unknown operations. Limits are 1,600 forwarded requests total, two scan minutes per service, one minute per rule, two threads per host, a five-minute scanner process timeout per service, two fixture users, two uploads and zero worker invocations. [Exclusions and limits][dast-limits], [request guard][dast-guard].
>
> Successful execution requires a well-formed local-target report, a successful response on every imported route, no in-scope authentication denials, no exceeded request cap, an unchanged/valid fixture session and resources, no cookie forwarded to object storage, and cleanup. Scanner/report/coverage/cleanup failures fail the job and Full verification. Finding severity is deliberately report-only. Sanitized findings and disposition retain source SHA, scanner image, source/scan schema hashes, route coverage and cleanup without publishing private cookie jars or raw reports. [Report validation][dast-report], [coverage check][dast-coverage], [disposition and return policy][dast-result], [cleanup][dast-cleanup], [publication][dast-publication].
>
> The 25 October hosted result on the baseline SHA was 7 exercised routes and 16 findings, with 146 out-of-scope requests blocked and cleanup PASS. The main CI run nevertheless failed in separate inherited image-scan jobs. No scan against deployed CloudFront, API Gateway/authorizer, real S3 redirects or IAM is established. Cloud-edge DAST remains `NOT_RUN`. [Hosted receipt][ci25], [explicit cloud boundary][dast-cloud].

Method references supplied by R5 F9: [OWASP DevSecOps Guideline](https://owasp.org/www-project-devsecops-guideline/), [ZAP API Scan](https://www.zaproxy.org/docs/docker/api-scan/) and [NIST SP 800-218](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf). These describe practices/tool behavior; they are not execution evidence for this repository. No Semgrep integration or passive-baseline run is implied.

### CODE-DAST-CLOUD: candidate-bound staging cloud-edge DAST (proposed / NOT_RUN)

- Define the authorized target environment, allowed origin/routes and ownership. Prefer a disposable staging deployment of the candidate. A production scan cannot attest to an unpromoted candidate.
- State whether CloudFront, actual API Gateway/authorizer, S3 redirects and IAM are in scope. Bind source SHA, image/config IDs, aliases, OpenAPI hashes and scanner/policy digest to the target. Require explicit readiness, not only a live URL.
- Seed isolated synthetic owners/content and prove owner, other-owner and anonymous controls. Obtain credentials privately. Keep authenticated requests at the authorized origin. Expand mutation/HLS/admin coverage only with safe fixtures and cleanup design.
- Retain sanitized JSON/SARIF, target/source identity, route coverage and cleanup proof. Exclude cookies, signed URLs, raw response bodies and account data. Decide whether publication failure blocks.
- Acceptance: real source-matched hosted receipt for the staging target, positive/negative ownership controls, bounded scan, defined coverage and successful cleanup. Until then label cloud DAST proposed / NOT_RUN.

### CODE-DAST-POLICY: blocking finding disposition (proposed)

- Separately define execution failure, incomplete coverage, finding severity and approved exceptions. Preserve fail-closed scanner/coverage/cleanup behavior already present.
- Agree blocking severities, triage, accepted-exception owner/expiry and the consumers of the result: PR CI, release admission and restore. Do not turn an arbitrary nonzero ZAP exit into a severity policy without validating retained reports.
- Test meaningful policy cases: threshold findings, allowed/expired exception, malformed/missing report, wrong target/source, incomplete authenticated route coverage and cleanup failure.
- Acceptance: documented rule, focused policy/integration checks and a real hosted receipt showing its actual disposition. Report-only remains the current finding policy until implemented and evidenced.

### CODE-BRANCH-PROTECTION: enforce selected repository checks (proposed configuration)

- Agree Main ruleset/branch protection, required stable check names and bypass policy with the team. Decide how separate CodeQL analysis / security review should participate rather than inferring enforcement from its existence.

- Acceptance: dated repository-settings receipt plus a controlled verification that a failing or missing required check prevents merge, with bypass rules recorded. Do not label the current team practice an enforced merge gate.
