3. Logical architecture
Lambda REQUEST authorizer · Cookie identity · TTL 0W1 · Authorization
Start at HTTP API and trace its call/return to MediaAuthorizer, then its separate call to the selected API. The normal Browser → CloudFront → HTTP API path is on s20. This is a custom Lambda REQUEST authorizer, not Gateway's managed JWT authorizer. HS256 requires sub, exp and iat; sub must be a UUID. session_token requires exactly one cookie-list entry parsed with access_token. SimpleCookie collapses repeated names within one entry; this is not strict raw duplicate-name rejection. A missing Cookie identity source is rejected by Gateway before Lambda invocation. With a valid JWT, the authorizer reads the current users row; user and operator map to publisher. Invalid input, unsupported role, missing user or lookup error deny. Success returns schema_version=1, integration=dc2-gateway-v1, owner_id and role=publisher. GatewayAdapter reads requestContext.authorizer.lambda, validates Actor, removes client x-owner-id/x-role and retains cookies. Media still validates cookie and current user and compares Actor; admin checks operator in SQL. Processing holds no Media secret or user-table credentials, but protected Processing requests reaching the authorizer depend synchronously on the Media lookup. Public bypass is GET /api/media/health, GET /api/processing/health and POST /api/media/auth/register, /login, /logout. execute-api remains directly reachable with the same authorization.
