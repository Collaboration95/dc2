5 · DevOps and development lifecycle

Slide 30 · “One repository, three images, per-service releases” · 1:00 · 5a

On screen: the repo box on the left, three images and their aliases in the middle, the branch row along the bottom. Do: point at the repo box, then the three images, then follow the branch row from left to right.

Thanks, Ibrahim. Section five is how a change gets from a laptop into that environment.

One repository holds both services, both clients, the infrastructure and the pipeline. We chose that so a contract change and both of its consumers land in one pull request. Separation is enforced inside the repository. Each service has its own CI lane and its own image, and an image build fails if it can import the other service’s code.

(point at the images) A release is identified by three things: the commit, the digest of the image we scanned, and the Lambda alias that serves it. CI and CD keep their scan reports, coverage and delivery records, and we commit the sanitized ones. The run IDs on the next slides come from those records.

(follow the branch row) Feature branches merge into an integration branch, which merges into Main through one release pull request. A green build on Main deploys automatically.

Slide 31 · “CI: changed lanes on pull requests, full run on Main” · 1:00 · 5b

On screen: four stage cards, numbered 1 to 4, and two numbers below them. Do: touch each card in order, then the two numbers.

The checks, from left to right.

(card 1) On a laptop we run lint and unit tests, and the full stack locally if needed.

(card 2) On a pull request into the integration branch, a policy script runs only the lanes whose files changed. If it can’t classify a change, it runs everything.

(card 3) Into Main, every lane runs: 25 jobs in about seven minutes, with real Postgres, a browser test, image scans and an 80 percent coverage floor for each package.

(card 4) After the merge, full CI runs again on the merged commit. Only that run can trigger a deployment. The gate job also compares skipped jobs against the recorded plan, so a lane can’t quietly disappear without failing the build.

Slide 32 · “Release: the scanned image is the one deployed” · 1:15 · 5b

On screen: the top row runs from merge to the AWS sign-in; the bottom row runs from scan to upload test; a roll-back box; an orange miss chip. Do: follow the top row, then the bottom row, then the roll-back box, then the orange chip.

Deployment has no manual step.

(top row) CD first checks that a full CI run passed on that exact commit. It signs in to AWS through OIDC, so no AWS keys are stored in GitHub. It updates the stack, then releases each changed service separately.

(bottom row) For each service it builds the image, scans it with Trivy, pushes it, and checks that the digest in the registry is the one it scanned. Then it moves the alias and runs a smoke test.

(roll-back box) If the smoke test fails, CD moves the alias back to the previous version. We tested this with a deliberately broken release. Then an upload-to-playback test runs through the public API.

(orange chip) Merge to serving takes about 15 minutes with no image change, and about half an hour when both services release. Rollback restores the image, not the database schema, so migrations are additive only. We missed one target: a Processing release step took 10.1 to 10.3 minutes against a 10-minute target.

Two findings came from failed deliveries. On 21 October, CD stopped with this line: “Trivy has 1 fixable HIGH/CRITICAL.” Production kept running the previous release.

(question mark) The new image was clean. But CD also rescans the image it is about to replace, because that image is the rollback target. An advisory against it had been published the evening before. So the check blocked the very release that removed the vulnerable image.

(fix, tick) We kept the strict scan for the new image and for every image we keep. For the image being replaced, the finding is now written into the release report instead of blocking. The next delivery released it.

Slide 34 · “Paused Aurora made the deploy smoke test fail” · 0:45 · 5c

On screen: two red ✗ steps, each with a fix, ending in a green ✓. Do: move from left to right.

The second finding. Aurora pauses after five idle minutes. When a deploy changed no migration, nothing woke the database, and the smoke test’s login got a 503.

We added a retry on that first call: after 5, 10 and 15 seconds, at most three minutes, and every attempt is logged.

Then we split the database per service, and three deliveries failed again, this time on Processing, because its cluster pauses separately. Now the first call to each service is retried, and delivery has been green since.

If asked (sections 5 and 6)

  • Why separate services in one repository? Separation means each service owns its data, its release and its failures. Lanes, image import checks, IAM roles and per-service releases enforce that. One lockfile and one stack are still shared.
  • Why run CI again after the merge? A pull-request run tests a preview merge. CD trusts only the push run on the exact commit that landed.
  • How do you know production runs the scanned image? CD scans the local image, pushes it, and checks that the registry digest matches. The Lambda version records the digest.
  • Why not block on the old image’s finding? Blocking kept the vulnerable image in production. New and kept images are still scanned strictly, and the finding is written into the release record.
  • Does the smoke-test retry hide failures? It covers only the first database call to each service, only on 502/503/504, at most three retries within 180 s, and every attempt is logged. The release smoke test that runs after a migration is never retried.
  • Which scanners block a release? Backup B09.
  • Is D4 ECS auto-scaling? No. A launcher starts finite tasks from the backlog, capped at 3 by a database check, with a one-minute safety net. Nothing idle is billed.
  • Is the 72 MiB padding staging? It’s an MP4 free box. The video and audio streams are real and fully encoded; the padding only pushes the file over the 64 MiB lane limit.
  • What are the “bash: child setpgid” lines in D4? Bash job-control noise from running the publish in the background. It doesn’t affect the run, and all five jobs end done.
  • Why only 10 users in D5? The API stage throttles at 20 requests a second, with a burst of 50. More users would only measure the throttle.
  • Are the clips real? Yes. D1 is a browser recording from 23 Oct. D2–D5 are screen recordings of a real terminal against the live system, made on 26 Oct. Waits are cut (D2) or shown at 16× with a label (D4, D5). D5’s report recomputes every figure from the raw samples.
  • Why “not found” for owner B rather than 403? A 403 would confirm that the asset exists.
  • Why no live push today? We don’t change production right before a demo. The runs on slide 42 come from a real change on 22 October.
