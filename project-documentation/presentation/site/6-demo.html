6aSignificant use cases

Three paths cover what the platform exists to do: an owner turns a raw upload into playable video, a separate application does the same through the published contract, and a different owner cannot reach the result.

D1 · Owner uploads in the browser and plays back

Claim. One submission stores the source, creates a job, processes it off the request path and returns an owner-authorized player. The end-to-end flow is described in 4d.

Prerequisites. Owner A is registered and both databases are awake (see warm-up). The upload file is a short MP4 with audio, under 64 MiB, 60 s and 1080 p, so the job takes the Lambda short lane. The browser is a clean profile on the CloudFront address with developer tools closed.

Steps.

  1. Open the site, sign in as owner A (password typed off-screen or pasted from a password manager; the clip starts after the click).
  2. Open Upload, choose the prepared file, submit once.
  3. Keep on screen whichever job states the page actually shows (queued, processing). A fast job may skip one; the caption names what was observed.
  4. When the badge reads done, play the video: advancing frames and audible sound.
  5. Open Your videos and reload the page: the job is still listed, which shows the result is persisted and not page state.

On screen. Account label, file name, job badge, a playing frame, and the library list after reload. No presigned query strings: the address bar is cropped out while the player runs.

Length and cuts. 95 s: submit 10 s, processing 20 s of actual time kept, playback 35 s, reload 15 s, captions 15 s. Cut file-picker navigation and registration typing first; keep the submit click, the processing state and playback.

Cost. One short encode, about $0.0003, plus roughly $0.013 to $0.053 of Aurora time for a 4-minute raw take.

If the take fails. A job that ends failed is a real result: stop, note the job identifier, and re-record only after reading the job's error in the library. A 503 on the first call means a database was asleep; wait for the wake and repeat the warm-up, then take again. Record from the start rather than splicing two attempts.

D2 · Batch publish with the Publisher CLI

Claim. The Publisher is a second application that talks to the same public HTTPS contract as the browser. It imports no service code and holds no database credentials. See 3 · Producers and consumers.

Prerequisites. Owner A. A folder with two distinct small MP4 files (no large originals). A private directory outside Git for cookie jars. The CLI lives in the repository's locked Python environment. Every global option goes before the subcommand.

DEMO_MEDIA="https://$DEMO_SITE/api/media"      # CloudFront address of the live site
DEMO_PY=.venv/bin/python
"$DEMO_PY" -m publisher --base-url "$DEMO_MEDIA" --cookie-jar "$DEMO_PRIVATE/a.txt" --json login "$DEMO_EMAIL_A"
"$DEMO_PY" -m publisher --base-url "$DEMO_MEDIA" --cookie-jar "$DEMO_PRIVATE/a.txt" --json publish "$DEMO_VIDEOS" \
  | jq '{ok,files:[.files[]|{file,ok,job_id,error}]}'

"$DEMO_PY" -m publisher --base-url "$DEMO_MEDIA" --cookie-jar "$DEMO_PRIVATE/a.txt" --json status "$DEMO_ASSET_A" \
  --wait --max-polls 180 --interval 2 | jq '{ok,job:{id:.job.id,filename:.job.filename,status:.job.status}}'

The password is read from a hidden prompt at login; the cookie jar holds the session and is never shown. DEMO_SITE and the account addresses come from the private recording notes, not from the repository.

On screen. Left: the terminal with the three commands, filtered through jq to allow-listed fields only (the raw completed-job JSON contains signed URLs). Right, last 15 s: the same owner's library in the browser after a reload, now listing the two published files.

Length and cuts. 65 s: login 8 s, publish output 15 s, status wait 20 s (trimmed from the real wait with a caption), browser 15 s, captions 7 s. Cut repeated polling output.

Cost. Two short encodes, about $0.0006, plus roughly $0.017 to $0.067 of Aurora time for a 5-minute raw take.

If the take fails. If polls run out, continue status on the accepted identifier. Do not publish again, which would create a second job. A file the API rejects shows as ok:false with its error; replace that file in the folder and take again from publish.

D3 · A second owner is denied

Claim. Access depends on who is asking, checked at the API on every request; an identifier alone does nothing. See 3 · Access.

Prerequisites. The completed job from D2 (owner A). Owner B, registered and with its own cookie jar and no jobs.

"$DEMO_PY" -m publisher --base-url "$DEMO_MEDIA" --cookie-jar "$DEMO_PRIVATE/a.txt" --json status "$DEMO_ASSET_A" | jq '{ok,status:.job.status}'
"$DEMO_PY" -m publisher --base-url "$DEMO_MEDIA" --cookie-jar "$DEMO_PRIVATE/b.txt" --json login "$DEMO_EMAIL_B"
"$DEMO_PY" -m publisher --base-url "$DEMO_MEDIA" --cookie-jar "$DEMO_PRIVATE/b.txt" --json status "$DEMO_ASSET_A" | jq '{ok,error}'
"$DEMO_PY" -m publisher --base-url "$DEMO_MEDIA" --cookie-jar "$DEMO_PRIVATE/b.txt" --json output "$DEMO_ASSET_A" | jq '{ok,error}'
curl --silent --output /dev/null --write-out 'anonymous HTTP %{http_code}\n' "$DEMO_MEDIA/jobs/$DEMO_ASSET_A"

On screen. A's success first, so that the denial means something; then B's two error objects; then the anonymous status code (401 expected; owner B receives a not-found answer so the API does not confirm that the job exists). Last 8 s: owner B's browser library, which lacks A's video. The non-zero exit codes are the expected outcome; do not run this clip under set -e.

Length and cuts. 40 s. Cut login typing; keep the positive control, both denials and the anonymous code.

Cost. No encode. Roughly $0.007 to $0.027 of Aurora time for a 2-minute raw take.

If the take fails. If B can read A's job, stop: that is a defect, not a retake. If B's login fails, B's cookie jar is stale; log in again and repeat from the third command.

6bQuality attributes

Scalability is shown by spiking load and watching the AWS console. Performance is shown by a scripted run whose HTML report is built from the run's own output files. Maintainability is shown by pushing a real change through the pipeline into production.

D4 · Scalability: capacity follows work

Claim. No encoder runs while there is no work. Standard-lane work starts finite Fargate tasks, up to a cap of 3, and they exit when idle. Short work goes to a separate Lambda lane bounded at 2 concurrent invocations.

This is not ECS service auto-scaling. A launcher starts finite tasks when work is published, with a scheduled safety net; there is no service desired-count to watch. The ECS view therefore shows tasks appearing and finishing, and the cap shows as a plateau at 3 while further jobs wait in the queue. The mechanism is in 4 · Launcher.

Clips of 64 MiB, 60 s and 1080 p or less are admitted to the Lambda lane (4 · Lanes), so a small clip no longer exercises Fargate. The Fargate view therefore needs fixtures above 64 MiB and below the 100 MiB input cap. Two views are recorded: the Fargate burst and the Lambda burst.

Prerequisites

  • Read-only AWS access for the recorder (a named profile with ECS, SQS, CloudWatch and CloudFormation describe rights) and region ap-southeast-1. No deployment, quota change, manual task start or lane toggle is needed.
  • Baseline: zero running worker tasks and empty queues, checked in the console before the take. No other submissions are in flight.
  • Padded fixture, made off-camera: a 24 s, 640x360 clip with 70 MiB of padding in a free box. The streams are unchanged, so the encode is real; only the file size crosses the lane bound.
ffmpeg -y -loglevel error -f lavfi -i 'testsrc2=duration=24:size=640x360:rate=30' \
  -f lavfi -i 'sine=frequency=440:duration=24' -c:v libx264 -pix_fmt yuv420p -c:a aac -shortest "$DEMO_PRIVATE/short24.mp4"
python3 - "$DEMO_PRIVATE/short24.mp4" "$DEMO_PRIVATE/fargate24.mp4" <<'PY'

import struct, sys

Jars are logged in beforehand; two processes never share a jar.

D5 · Performance: a scripted test with an HTML report

Claim. A repeatable, scripted workload against the live public API yields latency percentiles, error rate and throughput, and a report generated from the run's own files sets them against the stated targets.

The run

The deployed API Gateway stage throttles at 20 requests/s with a burst of 50. A load above that would measure the throttle, so the recording workload is deliberately small: 10 virtual users for 60 s after a 5 s warm-up, five other-route passes of 5 s, and 5 concurrent logins. That is roughly 10 requests/s, under the stage limit. Before the run the stage throttle is read (read-only) and the count of 429 answers is reported separately in the output.

aws apigatewayv2 get-stage --api-id "$DEMO_API_ID" --stage-name '$default' --query DefaultRouteSettings
RUN=perf-$(date -u +%Y%m%dT%H%M%SZ); mkdir -p "$DEMO_PRIVATE/$RUN"
DC2_BASE_URL="$DEMO_API_BASE" DC2_USERS=10 DC2_SECONDS=60 DC2_WARMUP=5 DC2_OTHER_SECONDS=5 DC2_LOGINS=5 \
  python3 -m scripts.aws.v1.proof.generator | tee "$DEMO_PRIVATE/$RUN/generator.log" | sed -n 's/^DC2-RESULT //p' | jq '{ok,users,routes}'
python3 -m scripts.demo.perf_report --run-dir "$DEMO_PRIVATE/$RUN" --out "$DEMO_PRIVATE/$RUN/report.html"   # to be written, specified below
(cd "$DEMO_PRIVATE/$RUN" && python3 -m http.server 8765 --bind 127.0.0.1)

DEMO_API_BASE is the API Gateway address from the stack outputs. The generator registers a throwaway account itself, so no owner credential is involved. It is not read-only traffic: it creates one account in the live Media database.

Report specification

The renderer, scripts/demo/perf_report.py, does not exist yet. It uses only the standard library and writes one self-contained HTML file with inline CSS and inline SVG, no scripts and no external resources. It reads files in the run directory and nothing else.

The report shows, top to bottom:

  1. Header: run identifier, UTC window, workload (users, seconds, warm-up, logins), path ("recorder to CloudFront/API Gateway over the internet"), and the commit.
  2. Targets against actuals as a table with a pass or miss mark per row: status route p90 against 700 ms; error rate against 1% (errors divided by count, every failure included, 429 counted); login p90 against 2 s; short-lane median queue wait against 20 s when jobs.jsonl exists.
  3. Latency per route: count, errors, p50, p90, p95, p99, max in milliseconds, for the status route, the four other routes and login.
  4. Latency histogram and percentile bars for the status route, as inline SVG.
  5. Throughput over time: requests per second in 1 s buckets across the timed window, with the stage limit drawn as a line.
  6. Queue wait and lane split (optional input): short lane against standard lane, median and maximum queue wait, end-to-end time and the number of jobs per lane.
  7. Provenance: the sample count, the verified hash, and the names of the input files.

The report is a rendering of the run's files. Nothing in it is typed in, so a second run produces different numbers from the same renderer. The historical in-region benchmark (status p90 58.2 ms over 9,000 requests, 50 users for 180 s, from a Fargate task in the same region) appears only as a labelled reference row, because this run uses 10 users over the internet and is not a repeat of it.

On screen. Terminal while the generator runs (about 100 s of real time, trimmed with a caption to the start and the result), then the browser at http://127.0.0.1:8765/report.html scrolling through sections 2 to 5. The folder is served over HTTP because browser panes block file://.

Length and cuts. 65 s: command and start 8 s, trimmed run 7 s, result line 8 s, report 42 s. If long, shorten the other-route table, never the header, the targets table or the throughput chart.

Cost. No Fargate. Roughly 600 status requests plus a few hundred others (API Gateway $1.25 per million, so under $0.01) and about $0.017 to $0.067 of Aurora time for a 5-minute raw take.

If the take fails. A register or login stage failure in the result line means a database was asleep: repeat the warm-up and rerun. Many 429 answers mean the stage limit was hit; lower DC2_USERS and rerun, and keep the failed log. A missed target is a result and is shown as a miss in the report.

D6 · Maintainability: a change through the pipeline into production

Claim. A change reaches production only through a pull request, a full set of checks and an automatic deployment that ends with an upload-to-playback smoke test, with no manual step in between. The checks are listed in 5 · Laptop to production; the stages in CI and CD.

The change

The file is frontend/index.html, line 265, the subtitle of the signed-in Your videos page. No test asserts on this text.

-            <p class="muted">Everything you've uploaded, in one place.</p>
+            <p class="muted">Everything you've uploaded, in one place - ready to play.</p>

Production is a single-page application in a private bucket behind CloudFront. The Deploy step builds it, syncs it and invalidates the cache (the last CD log shows [frontend] start to done in 4 s). index.html is served with no-cache, so a reload after the deployment shows the new text.

Measured durations

Read with gh run list and gh run view on 22 Oct 2026 (gh-durations).

6.5 to 8.7 minCI on a pull request, six successful runs
6.2 to 11.8 minCI after merge to Main, median about 7.7 min
7.6 to 8.4 minCD, two successful runs (Deploy 4m13s, smoke 2m08s in the latest)

CD starts about 2 s after Main CI finishes. A change therefore needs about 7.5 + 7.5 + 8.5, close to 24 minutes of real time from opening the pull request to a new page in production. The recording captures all of it in one raw take (screen recording running, GitHub and the site in two windows) and cuts it to 85 s.

Which branch the pull request targets

The team's normal flow is feature branch to dev/closeout to Main. The pull-request CI selects checks for the changed files; a push to Main runs full verification, and only a green CI on Main triggers CD (5a).

Recommendation: open the demo pull request directly against Main. It still passes the pull-request check gate, and it produces the whole chain in one pass: pull-request CI, merge, Main CI, CD. Going through dev/closeout adds a second pull request, a second CI cycle of about 7.5 minutes and a second merge before the first deployment step can start, which doubles the raw wait without showing another mechanism. The cost of the shortcut is that dev/closeout falls one commit behind Main; it is brought level after the recording by merging Main back. This should be agreed with the team before recording, because Main carries the frozen release.

Merging changes production. The deployed text stays changed after the clip unless it is reverted by a second pull request, which repeats the 24-minute chain without recording. The change is small and harmless, so it can also stay; either way the team decides before recording, because the report describes the deployed system.

Steps

  1. Off-camera: a clean checkout of Main; the databases warmed (a cold database is the cause of the three 22 Oct CD failures, all 503 on the Processing smoke call).
  2. Start the screen recording. In the terminal: create the branch, edit line 265, commit, push. 
    git switch -c demo/library-subtitle Main
$EDITOR frontend/index.html          # line 265
git commit -am "Add a short suffix to the library subtitle" && git push -u origin HEAD
gh pr create --base Main --title "Library subtitle: ready to play" --body "Pipeline demonstration"
  3. Show the pull request page: the checks list turning from pending to green. Keep the start, one mid-run frame and the all-green frame; cut the rest. Run gh run list --workflow ci.yml --branch demo/library-subtitle for the timestamps.
  4. Merge (gh pr merge --merge). Switch to the Actions page: the push CI run on Main, jobs finishing, Full verification green.
  5. Open the CD run that started from it: the Refuse a commit without green CI job, then deploy live with Deploy and Smoke test, upload to playback succeeding.
  6. In the browser (already signed in, on Your videos): reload and show the new subtitle. Show the page source line if the viewer needs proof of the served file.

On screen at the end. The PR with merged state, the CI run with its SHA and green status, the CD run with the same SHA, and the production page with the new text. The same commit identifier is visible in the PR, the CI run and the CD run.

Cost. One CD run: Aurora awake for about 10 minutes (about $0.033 to $0.133), a smoke encode, and possible migration tasks. GitHub-hosted runners add nothing on the AWS bill.

If the take fails. A red check is a result: show the failing job, fix the cause on the branch, push, and continue; the recording keeps both runs. A CD failure on a 503 means a database was cold: re-run with gh run rerun --failed after warming, never start CD by hand. If the recording is lost, the fallback is the two runs listed in gh-durations (CI 39733112331 and CD 39733859422), shown through gh run view; those are real runs, but the clip then no longer shows a change appearing in production, and the clip's title names the date of the runs it shows.

Recording preparation

Most of the risk in the recording is state: auto-paused databases, unprepared accounts and fixtures, and contamination between measurements. These are all settled before the first take.

Warm-up of the databases

The Media and Processing Aurora clusters pause independently when idle and resume on first use, so the first database call after a pause can return 503 while the cluster wakes. A health check does not touch the database and is not sufficient. Before each take: sign in as owner A, load the library (Media), and make one Processing call (a Publisher status on a known job reaches it), both returning 200. Both clusters pause after 300 seconds without connections, so start each take within five minutes of the last request and keep gaps between takes under five minutes. A short upload just before recording is the simplest warm-up for both. The database resume behaviour is described in 4c.

Accounts, files and tools

  • Owner A (browser, Publisher, scaling jars) and owner B (denial). Passwords are entered at hidden prompts or pasted from a password manager; cookie jars sit in a private directory outside Git and are never on screen, nor are presigned URLs.
  • Fixtures: the short upload file for D1, the two-file folder for D2, the padded folder set and unpadded folder set for D4. All are prepared off-camera and listed in the recording notes with their sizes.
  • Tools installed before recording: the locked Python environment with the Publisher, FFmpeg and FFprobe, jq, the AWS CLI with the read-only profile, and an authenticated gh. No installation appears in any clip.

Screen layout

A clean browser profile with notifications off. 1920x1080 at 30 fps, terminal font large enough to read after compression, browser cropped to the page. The AWS console is set to region ap-southeast-1 with the ECS, SQS, CloudWatch and Lambda tabs already open and the account identifier cropped from the header. Export H.264 MP4 and check each final clip's length with ffprobe -v error -show_entries format=duration -of default=noprint_wrappers=1:nokey=1 CLIP.mp4; the six lengths and the hand-overs total 480 s or less.

Capture order

Fixtures, accounts and jars; warm both databases; D1; D2; D3; D5 (so no scaling load runs during the benchmark); wait until queues and tasks are zero; D4 Fargate; D4 Lambda; D6 last, because it changes production and can disturb the others for the length of a deployment.

Cost

Shared Aurora time dominates. Two clusters awake at 0.5 to 2 ACU each cost $0.20 to $0.80 per hour at $0.20 per ACU-hour, counted once for the whole session rather than per clip. A session of about two hours is therefore $0.40 to $1.60 of database time. Encodes add under $0.06 across all clips; D6 adds one deployment. These are estimates from the Singapore rates in the cost inputs (demo-cost), not an invoice. The mechanism is in 4 · Cost model.

Questions a professor may ask

Is the scaling in D4 an ECS auto-scaling policy?

No. A launcher starts finite Fargate tasks when work is published, guarded by a database-level fence so that it never exceeds the cap of 3, with a scheduled safety net for missed signals. A task takes one job and exits. An ECS service autoscaler would keep a desired count of idle, billable tasks and react to CloudWatch metrics with minutes of lag; finite tasks cost nothing at zero and match the workload of encoding jobs that run for tens of seconds. The price is a task start (image pull included) per job, which is why a short lane exists. See 4 · Launcher.

The fixture in D4 is padded to 70 MiB. Is that staging the result?

The padding is an MP4 free box that carries no media; the video and audio streams are those of a 24 s clip and are fully encoded. It exists because the lane decision uses source size (64 MiB), duration (60 s) and height (1080 p), so any small file is taken by Lambda and would not show Fargate. The clip states the fixture and shows the job going to the standard queue. The same padding was used in the earlier benchmark, so the Fargate figures compare like with like.

What does the Lambda graph prove, given a configured limit of 2?

The mapping's maximum concurrency is a bound, not a measurement. The ConcurrentExecutions graph over the burst is the observation, and it shows the actual peak: 2 if the jobs overlapped, 1 if they did not. The earlier short-lane comparison (queue wait 0.26 s against 32.6 s on Fargate, five jobs per arm) ran serially, so it proves lower queue wait and not concurrency. Total latency was not brought under 20 s: warm submit-to-done was 45.2 s and cold 92.0 s, and the keep rule failed on the cold median.

Why does the performance run use 10 users when the proposal says 50?

The deployed stage throttles at 20 requests/s with a burst of 50. Fifty users reading once a second plus logins would hit that limit, and the result would describe the throttle. The original 50-user, 180 s run needed the stage opened to 50 requests/s, which is a stage change the live environment does not get for a recording. The 10-user run shows the same tool and the same report; it is labelled as a smaller workload over the internet, and the 58.2 ms p90 figure from the in-region run is shown beside it as history, not as a repeat.

Why a status request as the main latency probe?

It is the call the browser makes repeatedly while a job is processing, so its latency is what a user feels and what scales with the number of waiting users. It requires authentication, a Media database read and an ownership filter, unlike a health check. A weakness is that the generator's account owns no jobs, so the query returns an empty list; it measures the request path and the index lookup, not a large library.

Are the clips live? Is anything simulated?

The clips are recordings of real actions on the deployed system; nothing is drawn in HTML, mocked or replayed. Waiting time is removed in editing and each cut carries the true elapsed time. The reason for pre-recording is timing control: an encode, a deployment or a database resume would otherwise occupy the audience's minutes. The cost is that the audience cannot choose what is shown; the raw captures and the run directories are retained.

Why does the maintainability demo merge straight into Main instead of dev/closeout?

Both routes pass a pull-request gate, but only a push to Main triggers the full verification and the deployment. Via dev/closeout the viewer would wait for an extra pull-request CI cycle and a second merge without seeing another mechanism. The cost is a temporary divergence between the two branches, closed by merging Main back, and an unreviewed shortcut around the integration branch; the pull request still needs green checks. Branch protection that forces a specific reviewer is not configured; discipline is by team convention (5a).

Why does owner B get "not found" rather than "forbidden"?

Answering 403 would confirm that the identifier exists and belongs to someone else. Returning the same answer as for a missing job leaks nothing about other owners' assets. Anonymous requests have no identity to check and receive 401. The check lives at the API boundary, so a guessed or leaked identifier is not enough; the datastores behind it do not enforce ownership by themselves. See 3 · Access.
