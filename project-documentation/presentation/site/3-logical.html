Section 3

Logical architecture and design

FlickPond is two services. Media decides who owns what and who may see it; Processing decides how a video gets encoded. They share no database and never call each other: they exchange messages through queues, and a small set of mechanisms keeps them consistent when messages are late, duplicated or lost.

3aDecisions that shaped the logical design

One decision drives the rest: split the system where the rules change, between owning a video and encoding it, and let the two halves communicate only through messages. Each decision below follows from that, and each has a price.

The requirement from section 1 is a reusable workflow (upload, process, status, playback) whose encoding capacity can grow and shrink without touching the user-facing API. The proposal drew a design for that with a synchronous call from Media to Processing, a Redis job queue and a shared service token. Moving to managed AWS services changed three of those choices, and the lecturer asked the team to confirm the service split with a detailed domain analysis. The decisions as built:

Layers inside each service

Both services follow the same layering. The API layer (FastAPI routes) receives a request with an already-trusted owner identity, validates the input and calls the domain layer. The domain layer holds the rules: for Media, upload intake, lifecycle (retry, edit, delete) and applying results; for Processing, command handling, the Attempt lifecycle and recovery. It decides whether a change is allowed, makes it, and stages any outgoing message in the same transaction. The persistence layer (SQLAlchemy models and Alembic migrations, one history per database) stores it. The shared kernel supplies the message envelope and the outbox/inbox machinery, identical in both images. The FFmpeg command builder is a separate pure package with no I/O, used only by the encoders.

Relationships that deliberately do not exist

  • Media never calls Processing, and Processing never calls Media.
  • Neither service can read the other's database. Each function's IAM role can read only its own service's connection string, and the database refuses the other service's login.
  • The encoder cannot send messages. It reports only by writing Processing's database; Processing's outbox publishes the result.

These are checked, not just documented: a build step fails if the other service's package, or any retired code from the old design, can be imported inside an image. check_runtime

Infrastructure is shared. Both services are defined in one CloudFormation stack, so network, queue and IAM changes for either service ship together; only code is released per service. The shared kernel is copied into both images, so a breaking contract change needs a release of each.

3cDomain-driven design, and how producers and consumers interact

Two bounded contexts, each with one aggregate that is its consistency boundary: the Asset in Media and the Job (with its Attempts) in Processing. Everything that crosses between them is a translated message, and a handful of fences make those messages safe to deliver late, twice or out of order.

Bounded contexts, context map and language

A bounded context is the part of the system in which a word has one exact meaning and one model enforces its rules. The proposal drew the boundary from the verbs of the workflow (upload, submit, claim, encode, complete, play). The detailed analysis then checked it against what the code actually has to keep consistent inside one transaction.

ContextOwnsDoes not own
Media ManagementAccounts and login, ownership, upload intake, source versions, playback signing, the public job view, deletion and source cleanup (media_db)Job state, attempts, leases, outputs. It holds only a projection.
ProcessingJobs, attempts, leases, retry and cancel, output descriptors, cleanup of late outputs, encoder claims and launch reservations (processing_db)Users, Assets, source bytes (it has read-only access), playback links

Why the line is there. In media_db, assets, upload grants and request keys all have a foreign key to users; the authorizer, the upload grant and the playback signer all read those same rows. Owner and Asset belong in one transaction. Processing's rules (one job per video, one current attempt, a lease that decides which worker may finish) need none of that data; they only need to know the owner's ID as a plain value. Processing holds the owner as a UUID, never a foreign key.

The relationships on the context map:

  • Customer and supplier. Media is the customer: it says what should be processed. Processing is the supplier and owns the answer.
  • Translation on both sides (an anti-corruption layer). Media builds a submit message from its Asset and pinned source, and turns each result into its own projection and public status. Processing turns each command into its own rows. Neither imports the other's code.
  • Published language and shared kernel. The message envelope, the owner-identity format and two OpenAPI documents. The code that defines them is copied into both images, which is why it counts as a shared kernel: changing it affects both sides, so it has a versioning policy (see contract).

There are five message kinds, all in one envelope: submit, retry and cancel (Media to Processing), work (Processing to an encoder) and result (Processing to Media). There are no separate domain events such as "JobStarted". Every change to a Job (claim, completion, failure, retry, cancel) produces one result carrying the Job's full state and an increasing state_version. This style is called event-carried state transfer. It is not event sourcing: the SQL rows are the truth, and messages are copies of it.

Asset, Job and Attempt

An aggregate is a cluster of rows that is changed only through its root, inside one transaction, so its rules always hold. FlickPond has two, and no transaction ever spans both.

Why a Job has Attempts. A retry must not overwrite the history of the failed try, and a slow worker from the old try must not be able to write a result for the new one. Giving every try its own row, number and output folder (jobs/{job}/attempts/{attempt}/) makes "which try is this result for?" a question the database can answer.

Source pin: the bytes checked are the bytes encoded

An upload grant is valid for 15 minutes. During that time the client could upload a second file to the same key, and S3 would accept it. If Processing simply read "the file at this key", it might encode bytes that were never checked. The source pin prevents that: the source bucket keeps every version of an object, and Media records the one version ID it verified. Every later reader asks for that version and nothing else.

The database enforces part of this directly: a finalized reservation must carry a real version ID (a check constraint), and an unversioned bucket is refused. Retry and edit reuse the stored pin, which is why a retry never needs a re-upload.

The client must hash the whole file before reserving; the browser reads it into memory to do so, which is acceptable at 100 MiB but would not be for multi-gigabyte files. A versioned bucket keeps old versions, so cleanup (expired grants, deleted Assets, late writes after expiry) is a standing background duty of MediaRepair.

The encoder's IAM permission to read the source bucket covers the whole bucket, because S3 cannot scope it to one owner. The binding to the owner's prefix and the pinned version is enforced in Processing's code before any read.

Outbox and inbox: moving a change from one database to another

The problem. Finalize must do two things: save the new Asset in media_db and tell Processing about it through SQS. These are two different systems and there is no transaction that covers both. If Media commits and then crashes before sending, the video is never processed. If it sends first and then fails to commit, Processing works on an Asset that does not exist. This is the dual-write problem.

The outbox. Media does not send anything during the request. It writes the message as a row in its own message_outbox table, in the same transaction as the Asset. Either both exist or neither does. A separate step sends outbox rows afterwards.

The inbox. The sender may send a row twice (it cannot always know whether its last send succeeded), and SQS itself may deliver a message more than once. So every receiver first writes the message's ID and a hash of its content into its own message_inbox, in the same transaction as the change the message causes. A second delivery finds the ID already there and does nothing. The receiver tells SQS to delete the message only after that commit.

Who sends what: Media's commands are sent only by MediaRepair, on its one-minute tick, because the MediaApi function has no SQS permission. ProcessingCommands sends its own outbox right after its commit. An encoder's result (claim, done, failed) waits in Processing's outbox until the next repair tick, or until an S3 "object created" or ECS "task stopped" event triggers the same repair pass sooner. Each send of a work message also wakes the launcher.

Because only the one-minute tick sends Media's commands, a submit can wait up to about a minute in the outbox before it reaches the queue.

The outbox gives up immediacy and adds a table, a sender and repair logic to each service. In return a state change cannot be lost between the two databases, and Media keeps accepting uploads while Processing is unavailable. On AWS, with Processing's command consumer switched off for 48 s, Media still accepted an upload (202) and the job reached done 58.9 s after the consumer came back. r1018b

What happens when a message arrives twice

Delivery is at least once: every message arrives one or more times, possibly late and out of order. Exactly-once delivery is not available across a database and a queue, so each receiver is made idempotent: applying the same thing twice has the same effect as applying it once. Several layers each catch a different kind of repeat:

RepeatWhat stops it having an effect
The same message delivered againInbox: the message ID is already recorded, so the handler does nothing and the message is deleted.
A second submit for the same Asset with a new message IDSubmission guard: one row per Asset, locked first. An identical request is a no-op; a different one is refused.
A cancel that arrives before its submitThe guard records the cancel; a later submit is accepted as a no-op and never creates work.
A retry sent twiceRetry requests are unique per Job and request ID, so the second creates no new Attempt. A retry that overtakes its submit is rolled back, including its inbox row, so a later redelivery can succeed.
Two copies of the same workThe work message ID is fixed per Attempt and state version. The first encoder to claim moves the Attempt to processing; the second finds it no longer queued and drops the message.
An old or reordered resultThe projection ignores anything with a lower state_version or an older Attempt (see projection).
A client repeating a request after a timeoutReserve is idempotent per owner and request ID; retry and edit carry a request key; the Publisher stores an intent key per file and reuses it when it reruns.

Duplicates do occur in practice. In a nine-job burst on the live environment, the work queue received 18 sends for nine jobs; all nine reached done and the queues drained to zero without manual purging. LV-11

A check that killing a worker mid-encode never leaves duplicate outputs has not been run on AWS. The fences that should guarantee it (lease token, Attempt output prefix, cleanup of dead Attempts) are tested locally on real PostgreSQL.

Lease: which worker may write a result

Several things can try to finish the same Attempt: a duplicate work message, an encoder that was presumed dead but is only slow, or an old encoder still running after the owner retried. The lease decides which one is allowed to write.

All times are read from the database clock (clock_timestamp()), never from the worker, so a worker with a wrong clock cannot extend its own lease. No database lock is held while FFmpeg runs or files transfer.

A worker dies mid-encode. It stops heartbeating. If ECS reports the task stopped, the event handler fails the Attempt at once; otherwise the lease runs out within 60 s and the next repair tick does it. On AWS, a deliberately stopped encoder was noticed in 5.8 s against a 300 s target. r1017b The owner then retries: a new Attempt, a new output folder, the same pinned source. If the old worker was only slow and later tries to finish, its token no longer matches the current Attempt and the write is refused; anything it uploaded sits in the old Attempt's folder and is deleted by the cleanup scan, which repeats for a day to catch late writes.

There is no automatic requeue after a worker failure: the Job becomes failed and the owner decides whether to retry. A video that crashes the encoder therefore cannot loop forever, but the owner sees a failure that a second try might have fixed. The one automatic successor is the short lane handing a too-long clip to Fargate (4 · Lanes).

Projection: Media's own copy of each job

Media must answer "what is the status of my video?" and sign playback links without calling Processing. It keeps a projection: one row per Asset in processing_projections, holding the Job ID, current Attempt and number, state_version, status, outputs and error. Only MediaResults writes it, inside the same transaction as the inbox row.

Reads then never leave Media: GET /jobs/{id} loads the Asset (filtered by owner) and its projection, and signs links to the outputs listed there. The output-prefix check means even a malformed result cannot make Media sign an arbitrary object.

The projection is eventually consistent: it can lag Processing by the time a result takes to be sent and applied, and a lost result leaves it stale until repair or a newer result. In exchange, status polling, playback and the retry and edit pre-checks never depend on Processing being up, and Processing's database sees no read traffic from users.

Consumer contract: playing it

When the job is done, the job view carries a presigned URL to the MP4 that expires within 15 minutes; S3 serves it with range requests (206), so the player can seek. For HLS, the player requests the playlist through Media at /jobs/{id}/hls/master.m3u8; Media checks ownership and returns it with caching disabled. Each segment request is answered with a 307 redirect to a fresh presigned S3 URL. Video bytes therefore never pass through the API, and every playback still passes an owner check. Only file names matching a strict pattern are served.

Two clients on the same contract

The browser app is plain JavaScript with vendored hls.js and Plyr for playback. It hashes the file with the browser's crypto API, runs reserve → upload → finalize, and polls the job every 2 s. The Publisher CLI publishes a whole folder: for each file it reserves, uploads with a separate cookie-free HTTP client, finalizes, and optionally waits. It keeps a private journal of pending intent keys, indexed by file name, size and SHA-256, so a rerun after an uncertain network response reuses the same key and cannot create a duplicate Asset. It reports an outcome per file and exits non-zero if any failed.

Contract versioning

The HTTP contract is published as two OpenAPI documents (Media and Processing, both 1.0.0), generated from the code; a test fails if they drift. The message contract is one envelope with a schema_version. The rule for change: additions only within a version; consumers accept the current and the previous version and ignore fields they do not know; producers keep emitting the old version until every consumer reads the new one. Each consumer keeps a fixture file listing the fields it reads, and the producer's tests check its real messages against it. Additive changes can be released in either service first; a breaking change takes two releases.

Only version 1 has ever existed, so accepting "the previous version" is tested by raising the version number in tests, not by a real second version in production. The compatibility of a released pair of services is still an operator's attestation that those tests support.

How a release of one service is made and rolled back is in 5 · Continuous delivery and 5 · Rollback.

Questions a professor may ask

Why two services and not four (identity, media, processing, delivery)?

A service boundary is worth its cost when the two sides have different rules, data and reasons to change. Processing does: attempts, leases, retries, and a CPU-heavy load that scales separately. Identity and delivery do not: every playback or retry decision needs owner and Asset together, which today is one query in one database. As separate services, the authorizer, the upload grant and the playback signer would each need a call or a replicated copy of user data, and a delivery service would need to ask Media for ownership on every segment. That adds latency and failure modes without any independent scaling or release need. The proposal already rejected four services; the detailed domain analysis confirmed it against the actual foreign keys in the code.

The cost of staying at two: Media is the larger service and holds several concerns. If sharing or a second identity provider arrived, identity would be the next candidate to split.

Why not keep one database with two schemas? It would be cheaper.

Logically FlickPond already had that in V1: two databases on one Aurora cluster, with separate logins. That enforced ownership (neither login can read the other's tables), which is the property DDD needs. What it did not give was failure and capacity isolation: one instance, one capacity ceiling, so a burst of encoder writes or a failed resume affected both. On 21 October Processing was moved to its own cluster, created as a copy-on-write clone of the shared one; once a smoke test passes, each cluster's copy of the other service's database is dropped.

The cost is a second cluster's storage and its own resume delay after idle. Both clusters still scale to zero. A shared schema with cross-schema queries would have been cheapest of all, but it would let one service quietly depend on the other's tables, which is exactly what Project 1 suffered from.

Why asynchronous messages instead of a REST call from Media to Processing?

With a synchronous call, an upload succeeds only if Processing is up at that moment, so the two services' availability multiplies. With a queue, Media commits the upload and its outgoing message locally and returns; Processing picks it up when it can. This was shown on AWS: with Processing's command consumer off, Media accepted an upload and the job completed after the consumer came back.

The price is that delivery is at least once and possibly out of order, so the system needs the inbox, the submission guard, the lease and the projection fences. Status also becomes eventually consistent, which is why Media keeps its own projection. The alternative of keeping Redis/RQ was rejected because it needs a server running all the time, which conflicts with scaling to zero.

SQS is already durable. Why do you need an outbox?

SQS durability starts only once SQS has the message. The risk is the moment before: the Asset is committed in PostgreSQL, but the send to SQS has not happened or its reply was lost. There is no transaction spanning PostgreSQL and SQS. The outbox makes the intent to send part of the database commit, so a crash can only delay the message, never lose it. A lost reply just means the row is sent again, and the receiver's inbox absorbs the duplicate.

Alternatives: change data capture from the database log (more infrastructure), or a two-phase commit (not supported by SQS). The outbox costs a table and a sender per service.

Is processing exactly once?

Delivery is not; the effect is designed to be. Messages can arrive more than once, and work messages do (18 sends for nine jobs in one live burst). What prevents a double effect is layered: the inbox drops repeated message IDs, the submission guard allows one Job per Asset, a claim succeeds only on a queued Attempt, a finish needs the current lease token, and the projection ignores older versions. So the same video may be picked up by two encoders, but only one can claim it, and only the lease holder can record a result.

What is not yet proven on AWS is the case of a worker killed mid-encode followed by a retry, checked for duplicate output files. The fences that should prevent it are tested locally.

What happens if an encoder dies halfway, or an old encoder finishes after a retry?

The dead encoder stops renewing its 60-second lease. An ECS "task stopped" event, or the next repair tick after expiry, marks the Attempt abandoned and the Job failed; on AWS this was noticed in 5.8 s. The owner retries, which creates Attempt 2 with its own output folder over the same pinned source. If the first encoder was only slow and tries to finish, its lease token belongs to Attempt 1, which is no longer current, so the database refuses the write. Its files sit under Attempt 1's prefix and are removed by the cleanup scan.

An automatic requeue was rejected so that an input that crashes the encoder cannot loop. The cost is that a transient failure needs the owner's click.

Is this event sourcing, or CQRS?

Not event sourcing: the authoritative state is ordinary SQL rows in each service, and messages are snapshots copied from them; nothing is rebuilt by replaying a log. There is a separation of reads and writes in one place: Media's projection is a read model built from Processing's results and serves all status reads. That is a projection, not a full CQRS architecture: within each service, reads and writes use the same tables. Full Job snapshots were chosen over fine-grained events because they make out-of-order delivery easy to handle: the newest state_version simply wins.

Are the services really independent? What still couples them?

Independent: data (separate clusters and logins), code (a build fails if one image can import the other), release (each service is promoted and rolled back on its own, with the other unchanged), and runtime business flow (no synchronous calls). Still coupled: Processing's public routes depend on Media's authorizer and therefore Media's users table; both are defined in one CloudFormation stack, so infrastructure changes ship together; and the contract code is a shared kernel, so a breaking change needs two releases. These were accepted as proportionate for a three-person team; separate stacks per service and an identity provider outside Media would remove them at the cost of more operations.
