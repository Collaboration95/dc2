2. WHAT PROJECT 1 PROMISED AND WHAT EXISTS

- Accounts and permissions: basic registration, login, logout and owner/operator access exist.
  Profiles, password reset, email verification and account administration do not exist.

- Uploads: owned-video upload with input checks exists, with a 100 MiB limit.
  Resumable upload, measured transfer progress and malware scanning do not exist.

- Processing: FFmpeg processing, durable job states and duplicate-claim protection exist.
  A recovery task fails abandoned processing jobs and repairs some missed queue submissions.
  The retry API reuses the source. The browser retry currently uploads the remembered file again.

- Adaptive playback: MP4 and best-effort 360p/480p/720p HLS exist.
  The browser supports adaptive playback and MP4 fallback.
  This does not establish 4K, long-video capacity or guaranteed HLS for every input.

- Video management: a personal library, status filters, pagination and deletion exist.
  Titles, descriptions, tags, categories and Public/Unlisted/Private sharing do not exist.

- Discovery: a public homepage, text search and popularity features do not exist.

- External videos: YouTube references, metadata previews and embedded playback do not exist.

- Moderation: operators can list and delete jobs.
  Reports, review decisions, hide/restore and moderation audit history do not exist.

- Analytics: view counts, engagement metrics and product analytics do not exist.

- Downloads: signed processed-output access exists. An original-download endpoint does not exist.

- Editing: the backend supports crop, clip, downscale, upscale and conversion.
  Crop and clip widgets are missing. Some scaling and conversion controls exist.
  The baseline also supplies editing. It need not become a new Project 2 promise.

- Delivery: Compose, cloud hosting, TLS, tests, CI and security scans exist.
  Deployment remains operator-driven. Sonar and ZAP findings do not block the pipeline.
  A fresh normal Compose setup has a documented MinIO image problem.
  Automated deployment, Terraform and worker autoscaling do not exist.

The maintainer's 60% estimate describes overall progress.
This review does not calculate an exact percentage from features of unequal size.

5. THREE-DAY SEQUENCE

Day 1:
- Make the frozen baseline reproducible.
- Define the DDD model and contracts.
- Extract the basic Processing boundary and isolated persistence.
- Aim for one successful upload-to-playback flow before further scope.

Day 2:
- Complete boundary authentication and ownership checks.
- Integrate the small client and existing recovery mechanism.
- Adapt cloud deployment and CI in parallel where contracts permit.
- Resolve failing integration and security checks.

Day 3:
- Deploy the final revision and record the smoke test.
- Record worker scaling, interruption/retry, status latency and playback evidence.
- Use the remaining time for corrections and demonstration rehearsal.

If the core boundary still fails after day one, exclude optional polish first.
Do not spend the final day on new features.
If required evidence still fails, report the gap rather than claim completion.
An unresolved boundary or unavailable cloud environment can exceed this time limit.

6. WHAT WE WILL NOT PROMISE

- Completion of the remaining 40% of Project 1.
- Search, moderation workflows, external videos, sharing modes or product analytics.
- Crop/clip UI completion, thumbnails, 4K or a redesigned editor.
- Direct/resumable upload or a larger upload limit.
- AWS migration, Terraform, managed databases, Kubernetes or autoscaling.
- Historical data migration, a new token system or a complete backup/restore programme.
- A transactional outbox if the inherited reconciliation meets the chosen recovery conditions.
- Automatic recovery from host or availability-zone failure.
