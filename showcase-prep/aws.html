Chapter 03 / Project showcase · Cloud architecture

AWS: a small cloud, with clear boundaries

Follow one upload through the live V2 AWS system. Learn what each service owns, how work moves, and where the current design still has limits.

Three levels · approximately 16 minutes for the full chapter

Say it in your own words

The browser reaches our application through CloudFront and an HTTP API. Separate Media and Processing Lambda applications own their own data and queues. Video bytes go straight to private S3, while finite Fargate workers encode them. A bounded Lambda launcher starts those workers when work is waiting.

Level 1 / Understand the basics

Start with the shape of the system

Think of the project as two business services with a shared delivery path. Media owns people, assets, upload reservations, source ownership and playback grants. Processing owns jobs, attempts, retries, cancellation and worker leases. The services are separate because their data and release boundaries differ, not because every small feature needs its own service.

A visitor opens a generated CloudFront HTTPS address. CloudFront serves the existing frontend from a private S3 bucket and forwards /api/* to an AWS HTTP API. The API has explicit Media and Processing route groups. A Media-owned Lambda authorizer validates the login cookie and gives the API a trusted actor identity. Each service then checks that identity against its own records.

Read all diagram notes
  • Browser — The preserved frontend uses a generated HTTPS hostname. It never receives a database credential.
  • CloudFront — Static content comes from private S3 using origin access control. API requests pass through without caching.
  • HTTP API — The managed HTTPS API invokes the matching domain Lambda. Login and health have defined public exceptions.
  • Domain Lambda — The selected application checks ownership and writes only its own domain's database.
A useful first sentence

CloudFront is the public front door. The two domain applications own business decisions. Workers do the expensive video work.

Level 1 / Understand the basics

Follow the bytes separately from the requests

A video upload is large, so it does not travel through API Gateway or a Lambda request body. The browser asks Media to reserve an owner-scoped S3 key. Media returns a short-lived S3 presigned POST URL plus scoped form fields and a policy; the browser sends the file directly to a private S3 bucket. It then asks Media to finalize. Media checks the stored object and adopts its version as the owned source.

That check matters: a key supplied by a client is not proof that the caller owns the object or that the bytes stayed the same. Media controls reservation and adoption. A worker later receives permission to read the accepted source version and write job outputs. It cannot change or delete the source, read Media's database, or list arbitrary objects. Playback also uses a scoped grant; the output bucket is private.

Read all diagram notes
  • Reserve — The API creates an owner-scoped upload reservation and returns a bounded presigned POST URL, fields and policy.
  • Upload — Video bytes go directly from the browser to S3. This avoids API and Lambda payload limits.
  • Finalize — Media checks the stored object and binds an immutable accepted version to the asset.
  • Encode — Processing dispatches a job. A worker reads the accepted source and writes outputs to its job prefix.
Private is not the same as network-private

S3 objects are private because bucket policy and IAM control access. A signed URL still lets an authorized browser reach S3 over its public service endpoint for a limited time. The file is not kept inside the VPC.

Level 2 / Explain the design

Two databases, one shared Aurora cluster

Media and Processing each have a separate PostgreSQL database on one Aurora PostgreSQL Serverless v2 cluster. Each has its own runtime and migration credentials, schema history and owner application. Media's role cannot read Processing's database, and Processing does not borrow Media credentials. The services exchange versioned messages and identifiers rather than running cross-domain SQL.

The cluster is shared infrastructure, though. It is a common capacity and failure boundary, and activity for either database can keep it awake. An earlier observation held at 0.5 ACU, with Media repair and unretired upload reservations noted only as possible causes. Later, after the #273 backoff change, the accepted release recorded 0.0 ACU at 18:07 UTC on 19 October, about 56 minutes after the last upload. That is a point-in-time pause observation, not proof of monthly cost or sustained idle spend; later scheduled rescans can briefly wake SQL. The V2 experiment for one cluster per domain is implemented locally and has no live cloud evidence. It is not deployed. That pause observation was on daee44b, not a fresh idle-capacity measurement of runtime 629119c.

Read all diagram notes
  • Aurora cluster — The current layout has one Serverless v2 cluster. A shared cluster is cheaper and simpler, but a wake-up or capacity issue can affect both domains.
  • media_db — Users, assets, upload reservations, ownership and source adoption. Media runtime and migration identities are distinct.
  • processing_db — Jobs, attempts, leases, retries and durable message records. Processing runtime and migration identities are distinct.

The database sits in private subnets across two availability zones. Lambda functions connect to it through narrow security-group rules and TLS. Invocation-scoped database connections are important: a connection left open can stop Aurora from pausing. The subnet placement limits direct inbound reachability; it does not create independent databases or eliminate the shared cluster's failure boundary.

Level 2 / Explain the design

Messages coordinate work; SQL remains the record

The deployed system uses three standard SQS queues: Processing commands, Processing work and Media results. Each has a matching dead-letter queue for messages that exceed their retry policy. Messages carry identifiers and versioned facts, not the video itself, secrets or expiring presigned POST URLs and fields.

The important reliability pattern is an outbox. A service commits its business change and the message intent together in its own SQL transaction. A later publisher sends the queued intent. The receiving service records and deduplicates the message with its own state before acknowledging it. If a send or acknowledgement response is lost, retry and duplicate delivery are expected; the durable state and message IDs make recovery possible. SQL and SQS are not one atomic transaction, so repair code and monitoring still matter.

Read all diagram notes
  • Commit — Processing stores the job transition and its durable work intent in one SQL transaction.
  • Publish — A publisher sends a small work message. The queue coordinates delivery; it does not store source video.
  • Wake — An immediate Lambda wake and a scheduled safety tick inspect SQL, queue depth, and ECS task state.
  • RunTask — The launcher reserves a slot and asks ECS to start a task with a bounded deadline and unique identity.

This diagram is the control path, not the media-data path. The message tells a worker which accepted job to claim. The worker separately reads source bytes from S3 and writes encoded outputs back to S3. EventBridge is a wake-up and recovery hint, not the owner of job state and not a tunnel for media bytes.

Level 2 / Explain the design

Why Lambda coordinates and Fargate encodes

Lambda fits short, event-driven work: API requests, message handlers, repair passes and the launcher. AWS starts an invocation when needed, and the function ends when its bounded handler finishes. Fargate fits the existing FFmpeg pipeline: a task can hold more CPU and memory, download source data, encode multiple outputs, upload them, and stop when its one job is done.

The live worker task is 2 vCPU and 4 GiB, with one active encode. The launcher counts running, stopping and unresolved launches against a cap of three. It records a reservation before calling ECS; if a response is ambiguous, the next pass checks task identity or replays the same token and payload. This keeps concurrent launch attempts from casually exceeding the cap. Each task gets a finite lifetime and an absolute deadline, so an empty or stuck worker does not become a resident service.

LambdaHTTP APIs, queue handlers, short recovery and launch decisionsCold starts and account concurrency can delay bursts; a timeout bounds each invocation.

Level 2 / Explain the design

Subnet choices and the egress tradeoff

The current rendered V1 foundation places Lambda and Aurora in private, dual-stack subnets across two availability zones. The design has no NAT Gateway, paid interface endpoints, application EC2 host, load balancer or Redis service. Lambda uses IPv6 egress-only routing for AWS service APIs such as SQS, Systems Manager Parameter Store and ECS, plus an S3 gateway endpoint. The gateway path also permits the required regional container-image layer download path.

Fargate workers and migration tasks use public subnets with temporary public IPv4 while they run. Narrow security groups allow their database connection into Aurora; the database itself stays private. Public task placement makes image pulls and secret retrieval possible without a NAT Gateway, but it means those tasks have public egress and a temporary public address. Security groups, IAM and TLS still matter. Do not say every compute component is in a private subnet.

The dual-stack route is a cost-conscious choice. The rendered template defines the routes and endpoints; the V2-live deployment and upload-to-playback smoke show the deployed path works for that flow. Those checks do not prove every route, endpoint or failure case. Earlier architecture plans describe candidates and are not implementation receipts. Network privacy, IAM permission and S3 object privacy answer different questions; none substitutes for the others.

Say exactly what is private

Aurora is in private subnets; selected Lambda functions are attached to private subnets; Fargate tasks temporarily use public IPv4 subnets. S3 buckets are private by access policy, not because their objects sit inside the VPC.

Level 3 / Defend the details

Images, credentials and operational visibility

ECR holds the versioned container images for the Media API, Processing application and worker. Deployment inputs use immutable image digests so an environment can identify the exact artifact it runs. The API and worker are separate roles. The worker task role can read accepted source objects and write outputs, but has no Media database access. The worker does claim jobs and update Processing SQL directly: ECS injects its Processing database credential through the task execution role, which is separate from the worker's runtime task role.

Runtime secrets are stored as exact AWS Systems Manager Parameter Store SecureString references. The function reads only its own allowed parameter, and the database connection uses TLS with the RDS certificate bundle. ECS has separate task and execution roles: the execution role pulls images and injects task secrets, while the application role controls runtime AWS access. GitHub Actions uses GitHub's OpenID Connect identity to obtain short-lived AWS credentials for the deployment workflow; it avoids a long-lived AWS access key in repository secrets. This deployment identity is not the site's user login.

CloudWatch collects service logs and metrics. Alarms watch selected failure and backlog signals; EventBridge schedules repair and launcher work. The persistent V2 unattended launcher stays enabled by default. A monthly AWS Budget sends threshold notifications through SNS. A budget is an alert, not a hard spend ceiling. The live receipt recorded 13 of 13 named alarms in OK state at one time; that snapshot does not prove the alarms would catch every failure. The alarm snapshot was at 14:57 UTC on 19 October on an earlier source; it was not re-read for daee44b or 629119c.

The live V2 environment is persistent and its unattended launcher is enabled by default; workers still run as finite tasks. This is not the V1 operator workflow that opens and closes each session to enable and disable launch schedules. The V1 template remains the resource baseline, so keep those labels clear when describing deployed V2 behavior.

Level 3 / Defend the details

What the live measurements teach us

On 19 October 2026, a live three-clip run scaled from zero to three Fargate tasks and back to zero. It completed, but took about 37 seconds from queued work to the first job processing. Roughly 25 seconds came from task startup. That misses the 20-second queue-wait target. The launcher itself woke within about one second of a work send, so swapping the one-minute safety schedule for faster scheduling would not remove the main delay. The retained metrics file does not record a source SHA; it observed task definition dc2-live-worker:1, before the #272/#273 repairs. This is historical evidence, not a repeated measurement at 629119c.

A separate nine-clip backlog run completed in 239 seconds, at 2.26 jobs per minute, with a peak of three workers. This was one run at a fixed cap; there is no measured cap-1 or cap-2 comparison, so it is not a general capacity guarantee. The run initially left duplicate visible work messages after every job was done; a later recheck on daee44b recorded 9 of 9 jobs done and zero visible or in-flight messages without a purge. Duplicate sends still occurred (18 sends for nine jobs). Its source SHA is likewise not recorded. The later queue repair recheck belongs to daee44b: 9/9 jobs completed and the queue was empty. The current delivery did not repeat a 1/2/3-worker benchmark.

Why did processing take about 37 seconds to start?
The live V2 receipt attributes about 25 seconds to Fargate task startup. The rest includes queueing and launch overhead. A warm pool could reduce this wait, but would add idle task cost; the current design chooses zero idle workers.
Is a separate Aurora cluster per service deployed?
No. The deployed topology uses one cluster with two owned databases. Separate clusters are an implemented local experiment with cloud evidence marked NOT_RUN.
Does the object stay private if the browser has a signed URL?
The bucket remains private to ordinary callers. The signed URL is temporary delegated access, allowing that browser to transfer bytes through S3's service endpoint.
Why keep SQL if there is a queue?
SQL holds authoritative jobs, leases and durable send/receive records. SQS transports messages and can redeliver them; it does not replace transactionally owned application state.
Why not encode in Lambda too?
The current deployed encoder is a finite Fargate task with the existing FFmpeg engine. A short-encode Lambda lane is an optional V2 experiment, off by default, and its cloud measurements are NOT_RUN.
What does the monthly budget guarantee?
It sends alerts when configured thresholds are crossed. It does not prevent further spending or cap a running task by itself.

Before you move on

Can you explain these without reading?

  • Media and Processing own separate applications, databases, credentials and releases; they share one Aurora cluster in the deployed baseline.
  • The browser uploads media directly to private S3. SQS messages carry work metadata, and SQL remains the durable record.
  • Lambda handles APIs and bounded coordination. A launcher starts finite Fargate encoding tasks, capped at three, with no idle worker pool.
  • Aurora placement, subnet reachability, IAM permission and private S3 policy are distinct security boundaries.
  • Live V2 evidence shows successful 0-to-3-to-0 scaling, a 37-second queue wait, and a point-in-time Aurora reading of 0.0 ACU about 56 minutes after the last upload. It does not establish monthly cost or validate optional Lambda encoding and split-cluster experiments.
