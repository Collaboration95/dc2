Chapter 07 / Trust and access boundaries

Who can do what, and why?

Separate login, ownership, private storage, service identity and security testing. Follow the actual trust path.

Three levels · approximately 8 minutes for the full chapter

Say it in your own words

Media owns account authentication. API Gateway gets a trusted actor from Media’s authorizer, and each service checks that actor against its owned records. Video objects stay private, with narrowly scoped temporary grants for upload and playback. Cloud roles have separate permissions; security tests check specific boundaries rather than proving the entire system secure.

Level 1 / Understand the basics

Knowing who you are is only the first check

Authentication answers “who is making this request?” Authorization answers “may that person do this to this resource?” Arun can be logged in and still have no permission to read Maya’s job. A valid session is not a universal pass to every asset.

Media hashes account passwords with bcrypt and issues a signed JSON Web Token in an access_token cookie. The cookie is Secure, HttpOnly and SameSite=Strict. In plain terms, it is sent over HTTPS, withheld from ordinary browser JavaScript, and restricted in cross-site contexts. Those controls reduce risks; they do not replace endpoint authorization.

The Media-owned authorizer verifies the token and reads the current user record. Processing receives the resulting actor identity, not Media’s JWT signing secret or a copy of its users table. It still checks ownership of its own jobs. The design therefore has a real dependency: if Media’s authorizer or account lookup is unavailable, protected Processing requests cannot simply bypass authentication.

Is authentication enough to stop one user reading another user’s video?
No. Authentication identifies the caller. Every protected resource operation also needs an ownership check. A logged-in Arun must still be denied access to Maya’s asset or job.

Level 2 / Explain the design

The client cannot choose its own identity

Read all diagram notes
  • Browser session — The client presents a session token. Supplying an x-owner-id header is not a way to choose a different owner.
  • Media authorizer — Media verifies the token and current account, then returns a structured Actor in API Gateway authorizer context.
  • Gateway adapter — The adapter takes identity from the authorizer context and strips caller-supplied identity headers. Resource policies must protect direct Lambda invocation too.
  • Owner check — Media or Processing checks the actor against its own resource records before permitting the requested operation.

The adapter rejects missing or malformed trusted context and does not accept x-owner-id or x-role as authority. Authorizer caching is configured with zero TTL so the decision is based on the current account lookup rather than a cached role decision. A magic-looking marker in a JSON payload is not authentication by itself; callers must also be prevented from directly invoking a privileged Lambda with forged events.

Why not share the JWT secret with Processing?
Media owns account identity and current account state. A trusted Gateway actor lets Processing enforce job ownership without duplicating the user database or holding Media’s signing secret. The tradeoff is its protected API depends on the Media authorizer.
What stops someone sending x-owner-id with another user’s ID?
The Gateway adapter strips caller-supplied identity headers and uses the authorizer context instead. Service checks then compare that trusted actor with the resource owner. Cloud invocation policies protect the route into that adapter.

Level 2 / Explain the design

Temporary access is not a public bucket

An S3 bucket can reject anonymous access while allowing a narrowly scoped signed operation. Upload uses a presigned POST with a server-chosen key and policy fields. The grant limits what may be written; Media still verifies the object before adopting it. The client’s cookie is for the application and should not be forwarded to the storage host.

Playback begins with an owner-authorized request to Media. It returns short-lived output access rather than making the bucket public. Such a URL is a temporary capability: anyone who possesses a still-valid signed URL can use the permission it grants. Treat it as sensitive and avoid putting it in logs, screenshots or slides. It is not a permanent identifier or a separate login check at every media byte.

HLS needs more than a single MP4 object: a playlist names segments. The service validates output namespaces and handles scoped playlist/segment delivery. HLS generation remains best effort; MP4 is the playback fallback. Authenticated responses and responses setting session cookies use Cache-Control: private, no-store, including responses that carry playback access.

Does private storage mean a browser never reaches an S3 public endpoint?
No. Bucket privacy is an authorization policy. A signed operation can permit temporary access through S3’s public service endpoint. Private access policy and private network placement are different properties.

Level 3 / Defend the details

A user session and an AWS role solve different problems

IdentityPurposeExample boundary
User cookie / ActorWhich owner is asking for an application operation?Arun cannot read Maya’s job.
Lambda execution roleWhich AWS actions may this handler perform?Read only required configuration and use authorized queues/objects.
ECS task roleWhich AWS actions may running worker code perform?Read accepted sources, write outputs and consume permitted work.
ECS execution roleWhat may ECS do to start the container?Pull images, prepare logging and inject permitted task secrets.
GitHub OIDC deployment roleMay this workflow obtain short-lived AWS deployment credentials?The deployment pipeline does not need a stored long-lived AWS access key.

Database roles are another boundary. Media and Processing have separate databases, logins and migration ownership on the same Aurora cluster. A worker needs Processing’s database connection to claim and finish attempts, but it does not need Media’s account database. Sharing a physical cluster saves infrastructure while retaining logical ownership; it does not isolate failures at the physical level.

Message schema validation also differs from producer authentication. contracts/v1.py can reject malformed envelopes, secrets and URLs in messages. IAM and queue policies determine who may send and consume them. Correct-looking JSON from an unauthorized sender must not become a trusted command merely because it parses.

What is the difference between an ECS task role and execution role?
The execution role lets ECS prepare the task, including image pulls and permitted secret injection. The task role supplies AWS permissions to the application inside the running container. Neither is the same as an end user’s login.

Level 3 / Defend the details

How to discuss security without overclaiming

The project has multiple instruments. Owner and malformed-identity tests exercise application decisions. Ruff’s security rules flag static code patterns. Trivy examines packages in exact container images. ZAP runs bounded authenticated dynamic tests against the disposable local API harness. Retained AWS negative checks cover selected real cloud permissions and endpoints at an earlier source. None is interchangeable with the others.

The current image gate found zero fixable HIGH/CRITICAL findings, while unfixed rows remain. SonarCloud is unconfigured and must be described as NOT_RUN, not passed. DAST covers seven eligible GET routes from a 20-operation inventory and reports findings for review; it does not scan the deployed AWS edge. The latest upload-to-playback smoke also does not establish that every earlier AWS negative check was rerun.

A useful answer pattern

Name the threat, the control, the test that exercised it, and the remaining boundary. For example: “A forged owner header must not bypass authorization; the adapter ignores it, negative tests cover it, and real Lambda invocation policy is a separate cloud control.”

Is the system vulnerability-free because CI is green?
No. CI proves the required checks passed for a particular source and scope. Unfixed image findings remain, DAST has explicit exclusions and report-only findings, and SonarCloud is not configured. Green CI is useful evidence, not a universal security guarantee.
