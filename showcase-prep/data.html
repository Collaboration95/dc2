Chapter 06 / Data, messages and recovery

How does work survive failures?

Follow one accepted video through durable state, duplicate messages, worker leases and safe retries.

Three levels · approximately 9 minutes for the full chapter

Say it in your own words

We assume requests can be repeated, messages can arrive more than once and workers can die. SQL records the authoritative state. Outbox and inbox records bridge the queue boundary, source versions pin the exact bytes, and attempt leases prevent an old worker from completing newer work.

Level 1 / Understand the basics

An asset, a job and an attempt are different things

An asset is the owner’s video resource. A job is the work requested for that asset. An attempt is one try at executing that job. Keeping those ideas separate is what makes a retry understandable: the source stays the same, but the new attempt has its own identity and execution history.

The visible job state is queued, processing, done, failed or cancelled. Attempt records are more detailed: an attempt can also be abandoned, and a successful attempt uses the state succeeded. A job can move from failed back to queued when a legitimate retry creates a new attempt. That is not the same event as the queue redelivering an old message.

What is the difference between retrying a job and receiving a duplicate message?
A legitimate retry creates a new attempt for accepted work. A duplicate message repeats the same transport instruction and should not accidentally create a second logical operation.

Level 1 / Understand the basics

Uploading bytes is not yet accepting work

Read all diagram notes
  • Reserve — Media records an owner-scoped reservation with size, hash, type, expiry and a server-chosen S3 key. It returns a constrained presigned POST grant.
  • Send bytes — The client sends the file to the reserved object destination. The API does not proxy the full video body.
  • Finalize — Media verifies the object, pins its S3 VersionId, then commits the asset and processing outbox intent together.

The reservation expires after 15 minutes and the source limit is 100 MiB. Finalization checks the actual stored object rather than trusting the client’s filename or declaration. A hash identifies the expected bytes; the S3 VersionId identifies the exact object version the worker must read. Overwriting the same key later must not silently change an accepted source.

If the object is missing, finalization now returns a recoverable 409 with a safe message and adopts no asset or processing command. A genuine storage outage remains 503. An expired reservation is 410. These statuses tell a client whether to retry the same upload, start a new reservation, or treat storage as temporarily unavailable.

Why pin a VersionId when the object already has a key?
A key names a location whose contents can change. The version pin selects the exact accepted bytes, so a later write to that key cannot replace the source for an already accepted job.

Level 2 / Explain the design

The failure between saving and sending

Suppose Media saves an accepted asset, then crashes before sending its processing command to SQS. Without a durable record of the intended message, the asset could remain accepted forever without any work. Reversing the order is also unsafe: the queue could receive work for a database transaction that later rolls back.

Read all diagram notes
  • One transaction — The local SQL commit records the business change and its message intention together. Either both commit or neither does.
  • Publish later — A publisher claims a due row, sends outside the database lock, then records the outcome. Lost replies can cause another send.
  • Accept once — The consumer checks message identity, updates its own state and stages resulting messages in a transaction before acknowledging delivery.

The inbox records a message ID and body hash. Repeating the same ID and meaning can be recognized; reusing the ID for different content is a conflict. Outbox publication has its own claim token so an obsolete publisher cannot casually overwrite a later publisher’s outcome. SQL row locking and uniqueness constraints support these decisions under concurrency.

Why is an outbox needed if SQS is already durable?
SQS can preserve a message after it receives it. The outbox protects the earlier gap between committing our database state and successfully sending that message. It stores the intent in the same transaction as the business change.
Can we say exactly-once processing?
No. The transport is at-least-once. Inbox identity checks, idempotent state transitions and worker fences aim to preserve one correct logical result despite duplicates; they do not change the delivery guarantee.

Level 2 / Explain the design

Why a worker needs a lease

Starting a container is not permission to finish any job it chooses. A worker claims a current attempt and receives a time-limited lease token. Heartbeats extend its authority while it remains healthy. The database clock, current attempt and token determine whether a finish operation is valid.

Imagine worker A stalls. Recovery marks its attempt no longer live and allows later work. If A eventually wakes and uploads output, it must not replace the result of worker B. A fence checks that A still owns the current attempt and lease before accepting completion. Attempt-specific output paths also stop one attempt from overwriting another’s namespace.

Why is a queue visibility timeout not enough to protect completion?
It controls message delivery visibility, not ownership of the authoritative job state. A worker can continue running after its message becomes visible again. The SQL attempt and lease fence decides whether that worker may still publish completion.

Level 3 / Defend the details

A repeated click is an identity problem

A timeout does not tell a client whether the server committed. Publisher keeps a stable intent key for an uncertain mutation, scoped to the API base and authenticated owner. A repeat uses the same identity and original content. Once acceptance is confirmed, publishing the file again is a new user intention. This is not automatic directory synchronization or global deduplication of every identical video.

Media stores request identities and fingerprints. Reusing a key with different content is rejected rather than guessing the caller’s intention. Reservation finalization rechecks the row under a lock after object verification, so simultaneous finalize requests cannot both independently adopt it. The expensive object check runs outside SQL row locks to avoid holding a database transaction hostage during storage I/O.

Illustrative pseudocode — the actual code is linked below
verify_the_object_without_holding_a_row_lock()
with owner_database_transaction():
    reservation = lock_and_reload_reservation()
    if already_finalized:
        return_existing_asset()
    pin_verified_version()
    save_asset()
    stage_processing_command()
# The outbox publisher sends after this transaction commits.
Why not generate a fresh request key after every timeout?
The earlier request may already have committed. A fresh key means a new intention and could submit duplicate work. Reusing the original identity lets the server recognize the uncertain replay.

Level 3 / Defend the details

Deletion and repair are workflows too

Deleting a resource touches SQL state and object storage, so it has the same distributed-failure problem as processing. The application records a tombstone or cleanup intention, hides deleted content from the owner’s normal view, and retries object cleanup. A late result must not make a deleted asset visible again. A submission guard also handles cancellation that arrives before submission.

Repair must be bounded. Continually rereading old upload reservations can keep a supposedly idle database awake. The cleanup fix backs off rescans and eventually retires clean records after the relevant horizon; failed scans are not prematurely declared finished. The retained earlier freeze observed Aurora at zero capacity about 56 minutes after the last upload. That is a point-in-time observation, not proof of a monthly bill.

Know the remaining limit: configured backups are not a demonstrated restore drill, and the repository does not define a general retention deadline for all active media. Reliable failure handling is a set of explicit invariants and bounded repair paths, not a claim that failure is impossible.

Why not immediately remove every database row when an owner deletes a video?
Some durable state is needed to reject late messages, remember cancellation and finish cleanup after failures. Hiding the resource and recording deletion intent can be safer than forgetting the operation before all external effects are complete.
