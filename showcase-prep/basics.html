Chapter 01 / The project, without the jargon

What did we actually build?

Meet the users, learn the technology stack, and separate inherited capability from the work done in GC2.

Three levels · approximately 9 minutes for the full chapter

Say it in your own words

We built FlickPond into a reusable cloud video-processing platform. An owner uploads a video, conversion happens in the background, and the owner can follow its status and play the result. The browser and Publisher CLI use the same public contract. GC2 focused on separating responsibilities, running the system on AWS, proving reuse, and making delivery and recovery repeatable.

Level 1 / Understand the basics

Start with a person, not an AWS diagram

Imagine Maya has a folder of training clips. She wants usable videos, a clear result for every file, and a way to retry a failed conversion without uploading everything again. She should not have to know how to run FFmpeg, manage queues, or create storage permissions. Arun has the same need for one video through a browser.

FlickPond separates the quick interaction from the slow work. The application accepts an upload and records a job. A background worker converts it. The client asks for status until the result is ready. Acceptance means the platform has durably accepted the work; it does not mean the encode has finished.

Read all diagram notes
  • Upload — The client reserves a destination, uploads bytes to S3 and finalizes. A successful S3 upload alone is not yet an accepted job.
  • Track — The request returns before encoding finishes. The owner can check status while background work continues.
  • Play — The owner obtains fresh, temporary playback access after the output is ready.
  • Recover — A retry reuses the accepted source and creates a new processing attempt. It does not require uploading the original video again.
What problem does FlickPond solve in one sentence?
It lets an application turn an owner’s uploaded video into a trackable, playable result through a reusable API, without building its own storage and encoding workflow.
Why does the upload response not wait for conversion?
Encoding takes longer than a normal interactive request. Durable acceptance and background processing let the client return promptly and check progress separately.

A language, framework, database and cloud service are different kinds of things. Python expresses our program. FastAPI helps expose that program as an API. PostgreSQL persists its state. Lambda or Fargate runs packaged code on AWS. You do not need to memorize every package version to explain those responsibilities.

The frontend uses browser JavaScript and vendored playback libraries; Node and Vitest support its tests. The Publisher is a Python command-line program, not a second frontend framework. AWS infrastructure is rendered as CloudFormation from Python; Terraform and Kubernetes are not the deployed architecture.

Is the frontend a React or Node server application?
No. It is shipped HTML, CSS and browser JavaScript. Node-based tooling runs frontend tests; it is not a production application server.

Level 2 / Explain the design

Why call this a platform?

A single website can process videos. A reusable platform also exposes that capability through a stable contract so another application can use it. FlickPond’s core capability is owner-scoped media intake, processing and output access. The browser and Publisher both consume that capability through HTTP. They do not need database passwords, queue credentials or copies of the encoding implementation.

In platform language, the processing capability is the seed. Content owners produce input videos. Applications consume the APIs and processed results. The useful claim is demonstrated reuse through a second client. It is not a claim that we built a commercial marketplace or proved adoption by external organizations.

What concrete evidence supports the platform claim?
The browser and independently implemented Publisher use the published API for the same workflow. Publisher boundary tests ensure it does not import application internals or depend on database credentials. That is a bounded reuse demonstration, not evidence of market adoption.

Level 2 / Explain the design

What came from GC1, and what GC2 changed

StageWhat it meansWhat changed next
Inherited Project 1FastAPI app, accounts/uploads, job/retry concepts, Redis/RQ, MinIO, nginx, FFmpeg, MP4 and best-effort HLS already existed.GC2 reshaped these capabilities; video encoding was not invented from zero.
Submitted GC2 proposalA planned Media/Processing split with synchronous SubmitJob, Redis/RQ and a service token.The implemented design moved to SQL outbox/inbox, SQS and a trusted Gateway actor.
AWS V1Per-run stacks, separately owned data, three images, finite Fargate tasks and recorded cloud experiments.The accepted V1 tag remains immutable; experiments retain their own dates and workloads.
Persistent V2-liveOne dc2-live environment updated in place, bounded worker launch, idle pause design and automated delivery.The final engineering pass tightened quality and release verification while preserving the public workflow.
20 October engineering releaseShared credential policy, fewer dependencies, better integration discovery and failure tests, safe errors/cache policy, exact-source delivery gates.Runtime 629119c was delivered; later Main documentation is 8152ede.

The course work is therefore a story of architecture and operational maturity. We separated data ownership, made asynchronous work durable, demonstrated a second client, moved to managed cloud services, and checked failure behavior. The quality pass removed specific duplication and obsolete configuration while adding tests. Repository-wide physical line count increased after formatting and test additions; we should not claim that total LOC fell or every code smell disappeared.

Team history is separate from code history

The effort ledger records allocations and suggested specialisms. It does not verify each person’s actual hours or authorship. Confirm personal contributions with the team before using “I built” or assigning credit.

When a document and the code seem to disagree, check the document’s date and operating mode. The README contains older status snapshots, and the proposal describes an earlier plan. Use the engineering handoff for the latest retained delivery facts, then follow its code and test references. A local test using Moto emulates AWS APIs; a real AWS receipt is a different kind of evidence.

Why are Redis and MinIO dependencies still visible if the live system uses SQS and S3?
Some inherited paths and regression fixtures remain in the monorepo. Their presence does not put Redis or a MinIO service in the deployed AWS topology. Inspect the current image inputs, runtime paths and template to identify what actually runs.
