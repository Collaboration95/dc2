Chapter 01 / The project, without the jargon

What did we actually build?

Meet the users, learn the technology stack, and separate inherited capability from the work done in GC2.

Three levels · approximately 10 minutes for the full chapter

In short

We built FlickPond into a reusable cloud video-processing platform. An owner uploads a video, conversion happens in the background, and the owner can follow its status and play the result. The browser and Publisher CLI use the same public contract. GC2 focused on separating responsibilities, running the system on AWS, proving reuse, and making delivery and recovery repeatable.

Level 1 / Basics

Start with a person, not an AWS diagram

Imagine Maya has a folder of training clips. She wants usable videos, a clear result for every file, and a way to retry a failed conversion without uploading everything again. She should not have to know how to run FFmpeg, manage queues, or create storage permissions. Arun has the same need for one video through a browser.

FlickPond separates the quick interaction from the slow work. The application accepts an upload and records a job. A background worker converts it. The client asks for status until the result is ready. Acceptance means the platform has durably accepted the work; it does not mean the encode has finished.

Read all diagram notes
  • Upload — The client reserves a destination, uploads bytes to S3 and finalizes. A successful S3 upload alone is not yet an accepted job.
  • Track — The request returns before encoding finishes. The owner can check status while background work continues.
  • Play — The owner obtains fresh, temporary playback access after the output is ready.
  • Recover — A retry reuses the accepted source and creates a new processing attempt. It does not require uploading the original video again.
What problem does FlickPond solve in one sentence?
It lets an application turn an owner’s uploaded video into a trackable, playable result through a reusable API, without building its own storage and encoding workflow.
Why does the upload response not wait for conversion?
Encoding takes longer than a normal interactive request. Durable acceptance and background processing let the client return promptly and check progress separately.

Level 1 / Basics

The technology stack, layer by layer

Read all diagram notes
  • Clients — frontend/ is plain HTML, CSS and app.js loaded directly by the browser, with vendored hls.js and Plyr for playback; there is no production npm build. Node, Vitest and jsdom only run its tests. publisher/ is a Python command-line client of the public HTTPS API.
  • Python 3.12 services — media/ and processing/ expose FastAPI routes and validate requests with Pydantic. SQLAlchemy maps each service’s own tables and Alembic migrates each owner’s database separately. contracts/ defines the shared message values; media_engine/ wraps FFprobe and FFmpeg for the worker.
  • Three container images — deploy/v1/media, processing and worker Dockerfiles all start from python:3.12-slim. The Media and Processing images run the AWS Lambda runtime client. Only the worker image installs FFmpeg/FFprobe; it runs processing.v1_worker.
  • AWS compute — The Media and Processing images run as Lambda functions behind API Gateway, and CloudFront serves the static frontend. A launcher Lambda starts finite Fargate worker tasks, capped at three, when work is waiting.
  • Managed services — These run outside every container. S3 holds source and output video, three SQS queues carry work metadata, and one Aurora PostgreSQL cluster hosts the separate Media and Processing databases.
  • Delivery tooling — Not part of any request. GitHub Actions runs CI and CD. scripts/aws/v1/definitions.py renders the CloudFormation template that creates the AWS resources above; Terraform and Kubernetes are not used.

Python expresses the program, FastAPI exposes it as an API, an image packages it with its libraries, Lambda or Fargate runs it, and S3, SQS and PostgreSQL keep its files, messages and state. Delivery tooling sits outside the request path.

Is the frontend a React or Node server application?
No. It is shipped HTML, CSS and browser JavaScript. Node-based tooling runs frontend tests; it is not a production application server.

Level 2 / Design

Why call this a platform?

A single website can process videos. A reusable platform also exposes that capability through a stable contract so another application can use it. FlickPond’s core capability is owner-scoped media intake, processing and output access. The browser and Publisher both consume that capability through HTTP. They do not need database passwords, queue credentials or copies of the encoding implementation.

In platform language, the processing capability is the seed. Content owners produce input videos. Applications consume the APIs and processed results. The second, independently built client demonstrates that reuse.

Level 2 / Design

What came from GC1, and what GC2 changed

Read all diagram notes
  • 1 · Inherited Project 1 — Accounts, uploads, job and retry concepts, nginx, MP4 and best-effort HLS already existed. GC2 reshaped these capabilities rather than starting video encoding from zero.
  • 2 · GC2 proposal — The proposal used a synchronous SubmitJob, Redis/RQ and a service token. The implementation moved to a SQL outbox/inbox, SQS and a trusted Gateway actor.
  • 3 · AWS V1 — Separately owned data and recorded cloud experiments. The accepted V1 tag stays immutable, and each experiment keeps its own date and workload.
  • 4 · Persistent V2-live — Bounded worker launch, an idle-pause design and automated delivery.
  • 5 · 20 October release — Shared credential policy, fewer dependencies, better integration discovery and failure tests, safe error and cache policy, and exact-source delivery gates. Later Main documentation is 8152ede.

The course work is therefore a story of architecture and operational maturity. We separated data ownership, made asynchronous work durable, demonstrated a second client, moved to managed cloud services, and checked failure behavior. The quality pass removed specific duplication and obsolete configuration while adding tests. Repository-wide physical line count rose with the formatting and test additions.

The effort ledger records an equal planned allocation and suggested specialisms; it is not a per-person timesheet.

Level 3 / Details

Find the real implementation without getting lost

Read all diagram notes
  • Clients — frontend/ is the browser app and publisher/ is the Python CLI. Both use only the public HTTPS API, with ordinary owner accounts.
  • Media service — Accounts, asset ownership, upload reservation and verification, the local ProcessingProjection and owner-checked playback.
  • Processing service — processing/ owns jobs, attempts, leases, messages, recovery and the finite worker. media_engine/ holds the reusable FFprobe/FFmpeg probing and conversion code.
  • Shared libraries — contracts/ defines message shapes, source and actor identity and the Gateway adapter. delivery/ implements the SQL outbox/inbox and SQS transport. runtime_support/ holds small shared runtime policies such as storage credentials. Libraries only, with no database of their own.
  • Build and deploy — deploy/v1/ holds the three Dockerfiles. scripts/aws/ and deploy/aws/v1/ render, deploy and release the AWS stack, including the persistent environment despite the v1 folder name. .github/workflows/ runs CI and CD.
  • History and evidence — app/ and the inherited test stacks keep Project 1 behavior under regression; they are not on the AWS request path. docs/results/ and docs/release/ hold dated measurements and delivery receipts.

When a document and the code seem to disagree, check the document’s date and operating mode. The README contains older status snapshots, and the proposal describes an earlier plan. Use the engineering handoff for the latest retained delivery facts, then follow its code and test references. A local test using Moto emulates AWS APIs; a real AWS receipt is a different kind of evidence.

Why are Redis and MinIO dependencies still visible if the live system uses SQS and S3?
Some inherited paths and regression fixtures remain in the monorepo. The deployed AWS topology has no Redis or MinIO service; the image inputs, runtime paths and template show what actually runs.
