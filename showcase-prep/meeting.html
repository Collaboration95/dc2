Chapter 09 / From the course brief to a clear, honest demonstration

Prepare the GC2 project presentation

A practical guide to explaining Team 17’s Flickpond platform project: what the course asks for, how the design works, what the evidence actually shows, how to rehearse the demo, and which personal or course facts still need confirmation.

Three levels · approximately 15 minutes for the full chapter

Say it in your own words

We took an inherited video-processing application and separated its media and processing responsibilities behind contracts, then added a Publisher client and an independently operated cloud processing path. The result is a working platform with useful evidence and some honest misses: the small AWS scaling run passed at three workers but missed the two-worker target, and the proposed 30-clip AWS comparison was not run.

Level 1 / Understand the basics

A short opening that tells the truth

Use the 30-second version when the chair asks for a quick introduction: “Small teams need to turn video uploads into playable files without manually managing conversion. We started from an earlier Flickpond application, then built a platform path with separate Media and Processing responsibilities, an API-based Publisher client, and independently controlled cloud workers. We’ll show the user journey, the design, and what our measurements did—and did not—prove.” This names the problem, the seed, the reuse idea and the evidence boundary.

For a two-minute opening, add that Maya and Arun represent two individual content owners, while Jules represents an integrator and Sam an operator; these are fictional planning personas, not interviewed users. The browser and Publisher CLI are the two clients. The platform accepts an owned upload, processes it asynchronously and returns owner-authorized status and playback. Media owns identity and user-facing asset access; Processing owns attempts and encoding. The Publisher uses published contracts without importing service code or holding database credentials.

Then state the main result with its boundary: the retained AWS V1 six-clip run measured 1.449× at two workers, below the 1.6× target, and 2.347× at three workers, above the 2.1× target. This is not the proposal’s 30-clip experiment. A later V2-live nine-clip run used a fixed cap of three, so it is a separate observation, not a scaling comparison. Naming that early earns trust and sets up a useful design discussion.

Level 2 / Explain the design

Show the design, then name the evidence boundary

For logical design, explain two business contexts rather than listing boxes. Media owns accounts, assets, upload identity and owner-facing reads. Processing owns jobs, attempts, leases and encoding. Their contracts and data ownership let the worker capacity change independently. The SQL outbox/inbox makes work publication recoverable across a database and queue that cannot share one transaction; duplicate delivery is handled through idempotent processing. Trusted owner identity passes through the gateway so Processing does not accept a caller-forged owner header.

For physical design, show the current persistent V2-live arrangement as built: API Gateway and Lambda handle requests; SQS carries asynchronous work; S3 holds media; Aurora PostgreSQL stores service data; CloudFront serves the web app; finite ECS Fargate tasks encode. The two logical databases still share one Aurora cluster and one region, so this is neither physical database isolation nor a high-availability demonstration. Label diagrams that describe the earlier V1 deployment as V1 rather than quietly presenting them as the latest physical state.

Separate current engineering delivery from older experiment receipts. Runtime 629119c has a source-bound hosted CI/CD receipt and a post-deployment upload-to-playback smoke. That establishes the specific delivery and one smoke path; it does not refresh all earlier performance, security or recovery measurements. For scaling, keep the AWS V1 six-clip cap-2 miss and cap-3 pass visible. The proposal’s 30-clip AWS run was not done. V2-live’s nine clips at fixed cap three yielded 2.26 jobs/min in one run, while queued-to-processing was about 37 seconds against a 20-second target. Avoid combining local pre-V1 results with shipped AWS results.

For lifecycle, point from a change to tests, CI, image checks, admission, promotion and smoke evidence. State that unfixed scan findings remain; the gate is about fixable HIGH/CRITICAL findings, not zero vulnerabilities. The exact-source delivery receipt is in docs/results/engineering-20261020/delivery-629119c.json. A result from the earlier daee44b freeze keeps its own identity and limits.

Level 2 / Explain the design

Rehearse the live path and its fallback

Prepare an approved demo owner account, verify its login before the session, and use a small known-good clip below the 100 MiB upload limit. Keep a prepared folder and one job ID. Start the approved demo environment early enough to check the URL and health, and confirm the current live state with the team; a saved manifest is not a live availability check. Never show a password, token or private signed URL on screen.

  1. Maya submits the prepared folder with the Publisher CLI; show per-file outcomes and keep one accepted job ID.
  2. Open the browser as the same owner; show status moving to done and play the MP4. Mention HLS only if this item actually has it.
  3. Jules points to the public API contract and the CLI boundary; explain that the CLI needs no service import or database login.
  4. Sam uses a saved, source-labeled capacity or release receipt to explain independent operation. Do not trigger a risky scale or failure experiment during the presentation.

A known failed job may be used only if already prepared and verified: retry should use the stored source, not upload the remembered local file again. Never create a failure live just to make retry look dramatic. If login, upload, processing or playback stalls, say what failed, then switch promptly to a pre-captured screen recording or screenshots from the same stated environment and source. If no verified recording exists, use the retained receipt and a prepared local walkthrough, label it as recorded evidence, and do not present it as a live AWS result. The checklist says no recording identifier is attached, so recording access and the actual fallback files still need a human check.

Keep the fallback honest

Prepare the account, clip, job ID, receipt, and screenshots or recording before rehearsal. Label each backup with its environment and source revision. A screenshot proves only what it depicts; it does not prove the live system is still available.

Level 3 / Defend the details

Questions to expect and facts to confirm

Why split Media and Processing?
Media owns identity, assets and user-facing access; Processing owns encoding jobs and attempts. Separate ownership and contracts support independent worker capacity and releases. The trade-off is more operational and messaging complexity.
Does the platform prove the proposed scalability target?
Partly. In the AWS V1 six-clip run, three workers exceeded the 2.1× target at 2.347×, while two workers missed the 1.6× target at 1.449×. The proposal’s 30-clip AWS workload was not run. The separate V2-live run fixed capacity at three, so it is not a comparison.
Is the system highly available?
The evidence does not prove that. The deployment uses one region and one Aurora cluster/instance shared by both logical databases. Describe the chosen cloud services and recovery evidence without claiming regional or database high availability.
What did Team 17 inherit, and what did it add?
The baseline carries Flickpond’s earlier FFmpeg processing, HLS output, worker replicas and basic CI. GC2 work includes the Media/Processing split, service contracts and data ownership, Publisher client, AWS platform and delivery pipeline, security boundaries, and measured experiments. Keep inherited code and its original team’s effort separate from Team 17’s contribution.
How much did each person work, and who authored each design?
The ledger records 33 person-days / 264 hours allocated equally, or 11 person-days / 88 hours each, using eight hours per day. It is an allocation, not individual timesheets. Ask each person to confirm actual hours and contributions; do not infer authorship from commits or agent activity. A fair answer is a precise answer

Say what the receipt shows, which source and environment it used, and what remains unknown. A planned allocation is not a time log, a persona is not user research, and a successful smoke is not a complete quality-attribute result.
