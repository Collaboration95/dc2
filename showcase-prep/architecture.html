Chapter 02 / Architecture, from the owner’s first upload to playback

How the platform fits together

Follow the current Media and Processing design through its domain boundaries, durable hand-offs, worker path, and the trade-offs that keep the system understandable.

Three levels · approximately 14 minutes for the full chapter

In short

Media owns people, uploads, and playback access. Processing owns jobs and encoding attempts. They coordinate through versioned messages and each keeps its own database. A worker turns a pinned source version into outputs; Media then exposes those outputs only to the owner.

Level 1 / Basics

Start with the work the system promises

Think of Flickpond as a place where an owner submits a video, asks for a transformation, and later watches the result. The visible item is an Asset: a video owned by one account, together with its source identity and edit operations. Its identifier is also the public job identifier, so clients can keep one reference from upload through status and playback.

Processing work has a different life from the Asset. One Asset can have one Processing Job, and that Job can have several numbered Attempts over time. A retry does not overwrite the first attempt; it creates a fresh attempt from the accepted source. This distinction makes it possible to explain which try failed, which one is current, and which output belongs to it.

Read all diagram notes
  • Owner account — The account that may upload, read status and play outputs. Every protected read filters by this owner.
  • Asset — The user-facing anchor: source identity and edit operations. Its ID is also the public job ID from upload through playback.
  • Job — Processing’s lifecycle for the requested work. A unique asset_id prevents a second Job for the same Asset.
  • Attempts 1, 2, 3… — Each try has its own number, identity, lease and output path. A valid retry of a failed Job adds the next Attempt; earlier Attempts keep their history.
Why are Job and Attempt separate?
A job describes the requested processing over time. An attempt records one execution. Keeping them separate means a retry can be new work without erasing the failure history or confusing old and new outputs.

Level 1 / Basics

From client bytes to an accepted command

A browser or Publisher client first asks Media for an upload reservation. It sends a request key plus filename, declared content type, byte length, and SHA-256. Media validates the request and creates an owner-scoped reservation with a server-chosen S3 key. It returns a short-lived presigned POST. The client sends the bytes directly to S3, so a large video body does not travel through API Gateway or a Lambda function.

The client then calls finalize. Media verifies the uploaded object’s actual size, checksum, media type signature, and S3 VersionId. Verification happens outside SQL row locks because streaming bytes can take time. Media then locks the reservation and, in one database transaction, records the exact VersionId, creates the Asset, and stages a submit message. The accepted source is therefore not “whatever is currently at this key”; it is the immutable version Media checked.

Read all diagram notes
  • Reserve — Media fixes the key and expected file facts, then returns a short-lived upload grant.
  • Upload — The client transfers bytes to object storage without routing the video through the API.
  • Verify — Media checks stored bytes and records the S3 VersionId it actually verified.
  • Accept — One transaction adopts the Asset and records the command that will request processing.

This protocol has a cost: the client hashes the file before upload, and the system needs a versioned bucket plus cleanup for abandoned or late writes. That complexity buys a strong promise: the worker can later read the same bytes that Media accepted. A replay of an upload grant may create another object version, but the accepted source remains pinned to its original VersionId.

Idempotency makes uncertainty manageable. If a client repeats a reservation or finalization after a lost response, the request key lets Media return the already accepted item. Reusing the same key with different request data produces a conflict. This is especially important for Publisher: a transport timeout does not prove that the server failed to accept the file.

What if S3 has no object when finalize runs?
Media does not create an Asset or enqueue work. The missing upload is a recoverable client error, so the caller can retry or inspect the reservation without processing an unverified source.

Level 2 / Design

Two owners, with a deliberate seam

The design has two bounded contexts, Media Management and Processing. Each has its own vocabulary, rules, database role and code owner; the diagram below lists what each one decides.

They use separate PostgreSQL databases and roles (media_db and processing_db). Each service queries only its own tables and migration history. IDs crossing the seam are values in a contract, not foreign keys into the other service.

Media keeps a ProcessingProjection, a local read model of the latest accepted Processing state. A browser can ask Media for an owned Asset and its status in one domain. Media does not open a Processing database connection to answer that question. When a result arrives, Media validates it and updates its copy. Before the first result, Media can show accepted, a Media-side state that Processing does not emit.

Read all diagram notes
  • Media — Owns accounts, ownership checks, upload reservations, pinned sources, public reads, playback signing, deletion and cleanup. Its ProcessingProjection is a local copy of the latest accepted Processing state, so status reads never touch processing_db.
  • The seam — Versioned envelopes describe actors, sources, commands and results. contracts/ is a library both sides import; it runs nothing and owns no data. Messages travel over SQS lanes and land in each owner’s inbox.
  • Processing — Owns jobs, attempts, leases, retries, cancellation, output records and encoder claims. It decides which Attempt is current and whether a worker may claim or finish it.

Identity and playback stay with Media because those rules need the owner and Asset together. The user row, owner filter, source pin, and playback signer live in Media’s database. Splitting identity into a third service would make ordinary ownership and playback decisions depend on extra network calls, without creating a useful independent lifecycle. The architecture chooses two business services, not one service for every noun.

Is the Media authorizer a third service?
No. It is a separate execution role running Media code and reading Media’s user records. Service boundaries follow owned rules, data, and release units, not the number of deployed functions.

Level 2 / Design

Messages carry work across the seam

Media and Processing never call each other synchronously to create a job. Every hand-off is a message: the sender stages it in its own SQL transaction (an outbox row), a publisher sends it to one of three SQS lanes, and the receiver records it in its inbox with the resulting state change.

Why an outbox? A database commit and an SQS send cannot be one atomic operation. If the API changed SQL and then tried to send directly, a crash between the two could leave an accepted Asset with no command. With an outbox, the durable state change and intent-to-send commit together. A separate publisher can retry delivery. A claim token fences the publisher: after network I/O it acknowledges a row only if it still owns the claim.

Delivery is at least once, and Standard SQS can duplicate or reorder messages. The inbox stores a message ID and canonical body hash in the same transaction as the domain update. Repeating the same ID and body becomes a no-op; reusing an ID with different content is a conflict. Repair can reconstruct work from Processing’s SQL state if a queue entry is lost. These safeguards make the system recoverable; they do not make SQS exactly once.

Ordering is guarded at the domain level. Processing serializes submit, retry, and cancel with a per-Asset SubmissionGuard. Result snapshots carry increasing state_version values and attempt identity. Media ignores an older version, rejects conflicting content at the same version, and refuses an output outside the expected job/attempt path. An old worker may still finish a computation, but it cannot take authority from the current attempt.

Read all diagram notes
  • processing-commands — Media commits the Asset change and an outbox row together; a publisher sends it later. Processing accepts it into its inbox, serializes it per Asset and creates or changes the Job and Attempt.
  • processing-work — Processing stages work through its own outbox. A finite worker claims the Attempt with a lease and records the finish in processing_db. An optional short-encode lane exists as an unmeasured experiment.
  • media-results — Each Processing state change stages a result with an increasing state_version. Media validates it and updates its ProcessingProjection. The worker never writes to Media.
  • SQL in each owner — Within one database, state and message intent commit atomically. SQS delivery is at least once; the inbox absorbs duplicates and repair re-sends work that SQL says is still queued.
Does inbox deduplication mean exactly-once processing?
No. It makes repeated delivery of a message ID and body harmless for the domain transaction. Delivery can still repeat, and repair is still needed for the SQL-to-queue gap.

Level 2 / Design

From a worker lease to owner playback

The worker does not trust a queue message enough to start encoding. It asks Processing to claim the named Job and Attempt. Processing checks the source descriptor, owner and Asset identity, current-attempt status, submission guard, and finite task binding. If eligible, it creates a lease token and timestamps using the database clock. Heartbeats and finish operations must present that same live token before the deadline.

The worker downloads the pinned source, probes it, validates requested edits, and runs FFmpeg. Outputs live beneath jobs/{job_id}/attempts/{attempt_id}/. A successful attempt must report exactly one primary output; HLS is optional. Processing commits terminal state and result before the SQS work message is deleted. If a worker dies or loses its lease, its late completion is fenced out; the attempt becomes a visible failure/abandonment path and an owner retry creates a new Attempt.

When Media receives a result, it checks that the source matches its own accepted pin and that output keys belong to the stated attempt. It applies the state-version and attempt fences before updating ProcessingProjection. For MP4 playback, Media checks ownership and signs a short-lived S3 URL. For HLS, Media returns the playlist body and redirects segment requests to signed S3 locations. The playlist response is private and not cached. A foreign owner or unknown Asset appears not found.

Read all diagram notes
  • Claim — Processing grants one finite task temporary authority for the current attempt.
  • Encode — The worker reads the accepted version and writes namespaced outputs.
  • Project — Media accepts only a current, valid snapshot into its own read model.
  • Play — Media authorizes the owner and signs access to the completed output.

Failure example: suppose attempt 1 stalls, the owner retries, and attempt 2 starts. If the first worker wakes later and reports success, Processing’s lease/current-attempt checks prevent it from finishing as the authority. If a stale result nevertheless reaches Media through delayed delivery, the attempt number and state version prevent it from replacing attempt 2. The old output remains scoped under attempt 1 and is not the current playback result.

Why can a signed link expire?
The link is a short-lived capability to read one output. A fresh owner-authorized read can mint another; the system does not expose a permanent public object URL.

Level 3 / Details

Know the boundaries and the trade-offs

This architecture limits coordination; it does not remove shared infrastructure. Media and Processing have separate databases and IAM roles, but they share one Aurora cluster. A database pause or cluster problem can affect both. Media can accept and durably hold a command while Processing is unavailable, but encoding waits for finite worker capacity. In the V1 operating path, a person starts bounded batches; an opt-in V2-live launcher can wake finite tasks up to its cap. Neither is an always-running encoder fleet.

The Publisher CLI is a separate integrator, not another business service. It uses the public HTTPS API and has no application, database, or storage imports. That boundary lets another team automate folder publishing without receiving service credentials. The public contract is documented in the current OpenAPI files; contracts/ serves as the shared message language between service images.

Root-level app/ and app/worker/ contain an earlier monolithic runtime and are useful as history, but the current AWS-oriented V1 paths are media/, processing/, contracts/, delivery/, and runtime_support/. Some current files even say that behavior was extracted from app, such as media/api/v1_hls.py. The old app worker and Redis/RQ are not the active path; the current design records SQS plus SQL outbox/inbox and finite workers.

A useful design test is: does this abstraction protect a real invariant, boundary, or repeated policy? Repositories centralize owner-filtered SQL reads; application services compose business actions; adapters contain storage and transport behavior; contracts define cross-boundary values. More layers would not automatically help. A pass-through wrapper used once, another service for every feature, or a generic workflow engine would increase navigation and release coordination without protecting a rule.

Chapter summary

Key points

  • Media owns the Asset and a local copy of Processing status; Processing owns Job, Attempt, and output descriptors.
  • SQL is authoritative. Queues wake consumers, while outbox, inbox, repair, and version fences handle duplicate, delayed, or missing messages.
  • Uploads go straight to versioned object storage; the exact verified version is pinned before work is accepted.
  • A successful encode is not enough for playback: Media checks ownership and projection state before issuing short-lived access.
  • The old app package is not the current runtime architecture.
