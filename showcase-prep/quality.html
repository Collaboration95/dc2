Chapter 08 / Testing, coverage and security evidence

What the checks really tell you

Connect each test layer to the risk it covers, read statement and branch coverage, and see exactly what each security scan examined.

Three levels · approximately 12 minutes for the full chapter

In short

The project combines focused unit tests, owned service integrations, browser and command-line acceptance, exact-source coverage, image checks, and bounded dynamic scans. Each layer answers a different question; a passing summary is meaningful only when its scope, source and limits are clear.

Level 1 / Basics

Tests are layers of evidence

Each layer answers a different question, from a single rule to the built image. Cheap checks catch simple mistakes early; realistic ones exercise boundaries that mocks cannot reproduce. The diagram attaches each tool to the layer it serves.

The path classifier selects layers by ownership and risk. The Python fast lane runs the rule layer; owner integrations add real local services; Full mode adds the legacy PostgreSQL/MinIO/FFmpeg regression, Media and Processing integrations, Publisher HTTPS/browser checks, V1 acceptance and image/security evidence. The exact selected jobs are in the workflow and its receipt.

The 20 October offline receipt is source 514914a, not the later hosted Main source. Its complete regression recorded 3,697 passed, 267 subtests and two documented skips in 123.21 seconds; the same command passed 177 frontend tests. V1 recorded 157 selected cases, including 99 required cases; 13 optional short-encoder cases remain deferred. Offline evidence uses real PostgreSQL 16 plus Moto S3/SQS emulation for relevant V1 flows, not AWS-managed services. Hosted Main Full CI 39415935595 is a separate result for 629119c. The same source passed 73/73 exact-image execution checks across three Linux amd64 images, including packaging, imports, Lambda handlers, migration/bootstrap and FFmpeg checks.

Level 2 / Design

Coverage is a map, not a grade

Coverage asks which measured statements and decision outcomes ran during a test set. Statement coverage can miss a branch: a line containing if may execute while only one side is taken. The project tracks raw branch coverage as well as a combined statement-plus-branch measure. Branches matter in recovery code, where outcomes such as “lease is still current” and “lease has expired” must behave differently.

The combined backend gate joins five source-matched fragments: fast tests, legacy integration, Processing integration, Media integration and V1 integration. Each fragment includes metadata, and the validator checks the fingerprint against current source and expected omissions. A missing fragment or stale fingerprint is an error. Without those checks, combining numbers from different source versions could create a reassuring total that no single revision actually earned.

The global combined floor is 80%. In addition, Media and Processing each target 90% combined and 85% raw branches; the two recovery modules each target 80% combined and 75% raw branches. Package targets focus on owned service code, while recovery targets focus on high-risk state transitions. The report distinguishes these explicit floors from measurements reported without a floor. A green total does not erase a below-goal high-risk module.

For current local measured results, use the 20 October clean-source receipt 514914a. Media is 93.91% combined and 86.68% raw branch; Processing is 93.90% and 89.36%. Media recovery is 89.76% combined / 75.00% raw branch; Processing recovery is 88.34% / 80.00%. These meet their respective 90/85 package and 80/75 recovery floors. The hosted Main receipt later reports the same coverage measurements for source 629119c in Full CI run 39415935595; the two receipts stay separate. The 177 frontend tests measured 96.24% statement, 90.69% branch, 92.24% function and 99.55% line coverage, clearing four 90% floors. Vitest 4.1.12 changed AST coverage mapping from Vitest 2, so these percentages establish a new frontend tooling baseline rather than a direct trend comparison.

text
combined = (covered statements + covered branches) / (statements + branches)
raw branch = covered branches / all measured branches

Report: threshold + actual + source SHA + contributing test tiers

Coverage is not a direct measure of test quality. A line may execute without a meaningful assertion; a test may pass through a branch without checking the expected result. Coverage helps identify untouched behavior and missing outcomes. Read it alongside what tests assert, especially for retries, races, ownership and failures. Good coverage makes blind spots easier to discuss. It does not make a shallow assertion strong, nor does a lower number automatically mean a defect. It is one instrument in a review, so explain which behavior a missing branch represents and whether another test checks that invariant.

Why report raw branch coverage separately?
A combined figure can look healthy because many statements ran, while an important decision exercised only one outcome. Raw branches make that gap visible.

Level 2 / Design

Contracts and security checks target different risks

A distributed service often receives the same instruction more than once. A sender can lose an acknowledgement and retry even though the receiver committed the first request. Idempotency tests ask whether repeating an operation leaves one correct logical result. Fencing tests ask whether an old worker or stale lease holder is prevented from publishing after a newer attempt owns the work. These tests cover time and ownership, not merely the shape of one request.

The V1 contract fixtures freeze important public messages and response shapes. Producer and consumer checks validate envelopes, ownership, source identifiers and attempt/version fields. Persistence and recovery tests exercise tombstones, replay windows, reservation finalization and late-completion boundaries. A fixture proves compatibility with the recorded contract; it does not by itself prove real recovery timing or AWS delivery behavior. Executable and integration tests provide adjacent but distinct evidence.

Security checks also come in different forms. Ruff’s security rule set (ruff check --select S) is a static lint pass over source patterns. It can catch risky coding constructs early, but it is not a full security audit and it does not scan a built operating system. Trivy scans exact built images, including operating-system and Python package targets. The policy fails on fixable HIGH or CRITICAL findings; unfixed rows are retained and counted, not silently treated as fixed. “Zero fixable high/critical” does not mean “zero findings.”

SonarCloud is a separate advisory analysis, not a substitute for Ruff or Trivy. In Main CI 39415935595, both Sonar analyses were intentionally skipped because project configuration/credentials were not available. Record NOT_RUN; no clean Sonar result exists for this run.

The current exact-config Trivy receipts are from 20 October. For each of the Media, Processing and worker images, both the local validation scan at source 514914a and the deployed-image scan after delivery at source 629119c found zero fixable HIGH/CRITICAL rows. Unfixed rows remain 44 for Media, 44 for Processing and 208 for the worker in each set. These are finding rows, not distinct CVEs; repeated packages or image reports can repeat a vulnerability. CI scans identify the local Docker config ID and source; post-deploy scans freshly scan the retained deployed config/manifest identities. Neither result means zero vulnerabilities, and freshness/identity checks are part of the gate.

Static lint is one instrument

Ruff checks source patterns. Trivy checks packages inside the exact image. SonarCloud analysis is a separate advisory service. Their scopes do not substitute for one another.

Level 3 / Details

Dynamic scans have a bounded view

V1 dynamic application security testing launches a disposable local Gateway and authorizer harness, uses real PostgreSQL plus run-scoped Moto S3/SQS, then runs a pinned ZAP scanner against loopback HTTPS. It generates or validates the Media and Processing schemas and selects seven eligible GET routes from a 20-operation inventory (15 Media, 5 Processing). Request methods, routes, time and request volume are bounded; excluded state-changing or sensitive routes are blocked or tested with direct fixtures. This is authenticated local DAST, not a scan of AWS Gateway or every API operation.

The 20 October local validation receipt is tied to clean source 514914a. The initial unmodified DAST attempt completed Media but stopped before Processing requests; a separate confirmation completed both service scans. The confirmation exercised all seven selected routes successfully, with 317 handler requests and 146 out-of-scope probes blocked; no in-scope auth denial, server error or request-cap hit occurred. Eight low and eight informational entries remain. The first attempt and the confirmation are separate runs, and report-only findings remain open.

Full hosted Main CI 39415935595 separately passed its Linux DAST job for exact source 629119c. That is source-bound workflow evidence, while the detailed 317-request counts above belong to the local confirmation at 514914a. Neither scans AWS infrastructure. A green full gate means required workflow jobs and artifacts passed at that source; a NOT_RUN instrument, excluded route, local emulator or report-only alert retains its own boundary.

The simplifications are measured on specific code paired with preserved behavior and tests: shared native storage-credential policy fell from 253 to 175 source lines (78 fewer before Ruff formatting); the Media asset page now uses one owner-local outer join instead of an N+1 projection query, with focused SQLite assertions that one SELECT serves several page sizes; and image dependency exports narrowed from 44 packages to 40 Media, 36 Processing and 33 worker packages. These are targeted changes; repository-wide LOC rose, and the SQLite assertions count queries rather than measure PostgreSQL latency.

The DAST inventory says 20 operations. Were all 20 scanned?
No. The API inventory has 20 operations, and the active scan imports seven eligible GET routes. Other operations are excluded for explicit reasons and have direct contract checks where applicable.
What is SonarCloud’s status?
NOT_RUN: both advisory Sonar analyses were skipped in Main CI 39415935595 because configuration/credentials were unavailable. No Sonar pass is established.
What does zero fixable HIGH/CRITICAL mean?
The exact image config or deployed manifest had no HIGH/CRITICAL row with an available fix under the gate. The current receipts still list 44/44/208 unfixed finding rows across Media/Processing/worker; these are rows, not distinct CVEs.
Why is fewer code not enough to claim better quality?
A repository-wide LOC total does not show preserved behavior or covered failure paths. The stronger evidence is a concrete simplification (one SELECT instead of N+1, shared credential code, or narrower dependency exports) with its tests and exact source-bound results. Net repository LOC rose.

Chapter summary

Key points

  • Tests provide layered evidence; each tool covers one layer and one environment.
  • The 20 October coverage results meet the explicit Media/Processing and recovery module goals at their recorded source.
  • Offline regression, hosted Main CI, deployed-image scans and post-deploy smoke are separate receipts.
  • Trivy zero-fixable gates coexist with 44/44/208 unfixed finding rows; counts are not distinct CVEs.
  • Ruff, Trivy, SonarCloud, ZAP, actionlint and cfn-lint inspect different targets; SonarCloud is NOT_RUN and DAST has explicit exclusions.
  • Meaningful simplifications are supported by specific query, policy and dependency evidence, not a net LOC claim.
