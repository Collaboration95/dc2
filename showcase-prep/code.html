Chapter 05 / Implementation depth, from API handlers to worker leases

How the code turns design into behavior

Trace the current implementation by responsibility: thin route adapters, application services, repositories, storage and queue adapters, contracts, durable state, and the finite worker.

Three levels · approximately 13 minutes for the full chapter

Say it in your own words

The routes translate HTTP into application calls. Services coordinate rules and transactions. Repositories own repeated SQL access, storage and queue modules adapt external systems, and Processing’s lifecycle code fences worker authority. The layers exist to keep ownership, retries, and failure behavior visible—not to hide them behind a large framework.

Level 1 / Understand the basics

Read the code from the edge inward

When opening a codebase, start from a request the user can name. For upload, media/api/uploads.py declares the two HTTP endpoints and delegates to media.services.direct_intake. For jobs, media/api/v1_jobs.py delegates reads, retry, edit, and deletion. The route module owns HTTP details such as path, status code, response model, and dependency injection. It should be easy to scan without containing every database and storage decision.

The code then moves into an application service. direct_intake.reserve validates the media type, fingerprints the request, makes an owner-scoped reservation, and asks the storage adapter for a grant. direct_intake.finalize coordinates the reservation, remote verification, Asset creation, and command staging. This is orchestration: it gives the use case an understandable home while calling smaller pieces for persistence and external I/O.

A repository is a focused persistence helper. media/repositories/assets.py:get_asset applies the owner and deletion filters consistently and returns the same not-found result for an unknown or foreign Asset. list_asset_pages joins Media’s Asset to its own optional ProcessingProjection for a bounded page read. It does not join Processing’s database. Those helpers reduce repeated query mistakes while leaving transaction ownership with the caller.

Read all diagram notes
  • Route — Read the endpoint path, response status, authentication dependency, and delegated function.
  • Service — Follow business checks and orchestration across persistence and external systems.
  • Repository — Check owner filters, local joins, locking choices, and returned domain rows.
  • Adapter — Inspect how storage, queues, or HTTP contracts are translated and bounded.
Why not put all behavior in the FastAPI route?
Moving workflow decisions into an application service makes them easier to reuse and test, while keeping HTTP concerns local to the route.

Level 2 / Explain the design

Transactions make the promise precise

The most instructive function is direct_intake.finalize. It first looks up the reservation by both reservation ID and owner ID, checks that the request ID matches, and returns the existing Asset on replay. It then leaves the SQL transaction before calling storage.verify_direct_upload. The storage call can perform HEAD plus a bounded streaming GET; holding a row lock while waiting on network I/O would lengthen contention and increase the chance that an unrelated request stalls.

After verification returns the exact S3 VersionId, finalize opens a new transaction and locks the reservation. It rechecks whether another request finalized it or whether it expired during verification. If still valid, it records the VersionId and creates the Asset. Finally it stages the submit message before the same transaction commits. The important boundary is not “database versus storage” in general; it is: slow remote byte inspection outside the lock, then one short local commit that adopts verified bytes and records the intent to process them.

media/repositories/assets.py:fingerprint computes a stable SHA-256 of canonical JSON, and replay uses the (owner, operation, key) identity to make a repeat safe. If the key exists with a different request hash, it raises a conflict. Idempotency is a persisted rule, not an HTTP retry trick. It lets the browser or Publisher recover from a lost response without accidentally creating a second Asset.

SQL join choices should reflect ownership. list_asset_pages uses an outer join between Asset and ProcessingProjection. That join is appropriate because both tables live in Media’s database and the projection may not exist yet. If Media reached into Processing’s database for every status page, it would couple availability, permissions, and query latency across a service boundary. The projection duplicates a small amount of state to keep the public read local.

Read all diagram notes
  • Check — Confirm this caller owns the reservation and that the idempotency key matches.
  • Verify — Read stored bytes and obtain the exact object VersionId.
  • Adopt — Pin the version, create the Asset, and stage submit atomically.
What happens if the upload changes after verification?
The Asset points to the VersionId that verification returned. A later object write creates a different version and cannot change the accepted source descriptor.

Level 2 / Explain the design

Contracts and adapters keep neighbors at arm’s length

contracts/ is the published language between Media and Processing. contracts/v1.py validates an Envelope, its version, actor identity, immutable source descriptor, and allowed message kind. The contract contains values that cross the boundary; it does not import service models or make the databases shared. Version checks give producers and consumers room to roll forward additively.

delivery/sql.py and delivery/sqs.py adapt durable rows and validated envelopes to queue operations. The SQL helper stages an outbox row with the domain update, claims due rows, performs send outside the row lock, and acknowledges with a claim token. The SQS adapter enforces which producer and consumer lanes are allowed in code. Cloud IAM and queue resource policies enforce the same authority outside the process. The adapter is not the source of truth for a Job; the database is.

Storage follows a similar pattern. media/services/storage.py wraps S3-compatible operations used by Media: presigned POST, verification, cleanup, and signed outputs. Processing’s worker storage code handles source downloads and output puts. The two packages can wrap different use cases while sharing a narrow credential policy in runtime_support/storage_credentials.py.

That shared credential module provides static, ECS container, and Lambda credential providers. It rejects incomplete static pairs, refuses static overrides in ECS/Lambda mode, validates the container credential endpoint, and reads Lambda temporary credentials from the runtime environment. media/storage_credentials.py and processing/storage_credentials.py are intentionally thin facades: each reveals its own settings and calls the shared policy. This avoids copying security-sensitive selection logic while keeping each domain’s configuration independent.

Read all diagram notes
  • Domain — Each owner uses its own model and rules internally.
  • Contract — A small validated message carries identity and immutable source facts.
  • Adapter — Queue and storage modules translate external calls while SQL remains authoritative.
Why not share the storage client implementation wholesale?
The common credential selection rule is shared, while Media and Processing keep their own settings and storage operations. Reuse the policy that is truly common; keep domain-specific behavior near its owner.

Level 2 / Explain the design

Follow a command through durable state

In Processing, messaging.handle_command is the command entry point. It validates the envelope and trusted identity, accepts the message into the inbox, then uses a SubmissionGuard row to serialize submit, retry, and cancel for one Asset. A unique Job.asset_id prevents multiple jobs for one Asset. A repeated identical submit becomes a no-op; changed content under the same identity conflicts. A retry is accepted only from a failed state and creates a new Attempt.

State and notifications travel together. messaging.emit_state increments JobMessaging.state_version and stages a result snapshot in the same transaction as the state change. When Processing creates work, it stages a work message through the outbox too. A queue consumer commits inbox, domain rows, and any resulting outbox rows before its adapter acknowledges the record. The sequence protects against a process crash after commit but before acknowledgement.

The repair pass is not optional housekeeping. The SQL-to-SQS boundary cannot commit atomically across both systems. processing/recovery_v1.py:repair_work looks for queued Attempts whose work needs to be reconstructed. Media and Processing repair publishers retry outbox rows. Claims use tokens so a slow or resumed publisher cannot acknowledge work after another publisher has taken over.

Consider a failure: the SQS send succeeds, but the response is lost. The publisher does not know whether the message arrived and may send again. The duplicate gets the same message ID and body, so the consumer inbox makes the second delivery harmless. Another failure: the queue entry is gone but SQL still says queued. Repair creates a usable work message. The recovery story begins from committed SQL state, not from assuming a queue receipt tells the whole truth.

Result ordering is separate from duplicate detection. The inbox handles repeated message identity. media/projections.py:validate_transition handles stale or contradictory domain state: lower versions are ignored, same-version different content conflicts, lower attempts cannot replace a higher attempt, and terminal states cannot silently change. apply_result also checks owner, source, job, and output prefix before accepting a snapshot.

Read all diagram notes
  • Inbox — Same message ID and body is a duplicate; different body under that ID conflicts.
  • Version — A result must be current for the job, attempt, and increasing state version.
Why have both a message ID and a state version?
The message ID identifies transport delivery for deduplication. State version orders domain snapshots even when different messages arrive out of order.

Level 3 / Defend the details

The worker earns authority, then does bounded work

processing/worker/sqs.py:execute_message decodes a work envelope and asks Processing to claim it before fetching source bytes. The claim checks that the Job and Attempt match, that the source and owner match stored facts, and that the Attempt is current. It binds one finite task name to one Attempt. A malformed identity is not accepted as valid work; a stale message is acknowledged only when durable state proves it is stale.

processing/lifecycle.py:claim, heartbeat, and finish implement the time-limited lease. The database clock is the authority for lease and deadline comparisons. The worker renews SQL authority and SQS visibility together. Supervisor wraps potentially long operations so deadline or lease loss interrupts the pipeline. A worker that wakes after its lease expires cannot write a successful terminal result just because its local FFmpeg process finished.

processing/worker/tasks.py:pipeline makes the media transformation readable as stages: download the source; probe it; validate clip/crop settings; build the FFmpeg edit command; write the primary output; optionally build an HLS ladder for an unedited source; upload outputs. media_engine/ holds reusable probe, validation, operation, and HLS command construction. This keeps file-processing mechanics separate from queue polling and database lifecycle rules.

Output keys include both Job and Attempt IDs. This namespace lets late or abandoned workers leave isolated objects without overwriting the current attempt’s result. lifecycle.finish accepts the output descriptors only with the live lease and validates the primary output rule. HLS errors are caught as optional failure; lease loss, deadline, and cancellation still abort rather than being mislabeled as an optional-format issue.

The worker acknowledges work after terminal state and the result outbox row commit. If it fails earlier, redelivery or repair resumes from durable state. The next receipt may be claimable, stale, or sent to the dead-letter queue.

  • Lifecycle — Processing validates the current attempt and grants temporary authority.
  • Pipeline — The media pipeline transforms the pinned source and records namespaced outputs.

Level 3 / Defend the details

Thin Publisher, local reads, and the right amount of code

Publisher is a separately installable client. publisher/client.py:PublicClient uses the public API and imports no service or database models. The CLI hashes each file, reserves an upload, sends bytes with a cookie-free client, then finalizes. Its private intent journal reuses the same idempotency key after an uncertain response, without giving an integrator service credentials.

For status, Media reads its own Asset and ProcessingProjection. media/repositories/assets.py:list_asset_pages uses one bounded outer join to return a page and its optional projection. media/projections.py converts that row into the public response and checks whether the output is ready. For an HLS request, media/api/v1_hls.py rechecks owner access and that the job is done; playlist paths are constrained, the manifest is read privately, and segment paths redirect to signed URLs.

The older app/ package is historical, not the current worker path. Current V1 runs through media/, processing/, and processing/worker/sqs.py; its pipeline is in processing/worker/tasks.py. media/api/v1_hls.py notes that its route behavior came from the older app.

Before you move on

Can you explain these without reading?

  • Start at the route and follow imports into the service, repository, adapter, and transaction boundary.
  • A helper is valuable when it centralizes a real rule such as owner filtering, source pinning, or a live lease.
  • The direct upload finalize transaction couples Asset adoption with the outbox command; the external byte check happens outside row locks.
  • Outbox/inbox, claim tokens, attempt namespaces, and state_version address different failure windows.
  • The current path is media/ plus processing/; root app/ is an earlier implementation.
