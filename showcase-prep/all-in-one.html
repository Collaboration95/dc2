Chapter 01

What did we actually build?

Meet the users, learn the technology stack, and separate inherited capability from the work done in GC2.

We built FlickPond into a reusable cloud video-processing platform. An owner uploads a video, conversion happens in the background, and the owner can follow its status and play the result. The browser and Publisher CLI use the same public contract. GC2 focused on separating responsibilities, running the system on AWS, proving reuse, and making delivery and recovery repeatable.

Level 1 / Understand the basics

Start with a person, not an AWS diagram

Imagine Maya has a folder of training clips. She wants usable videos, a clear result for every file, and a way to retry a failed conversion without uploading everything again. She should not have to know how to run FFmpeg, manage queues, or create storage permissions. Arun has the same need for one video through a browser.

FlickPond separates the quick interaction from the slow work. The application accepts an upload and records a job. A background worker converts it. The client asks for status until the result is ready. Acceptance means the platform has durably accepted the work; it does not mean the encode has finished.

Read all diagram notes
  • Upload — The client reserves a destination, uploads bytes to S3 and finalizes. A successful S3 upload alone is not yet an accepted job.
  • Track — The request returns before encoding finishes. The owner can check status while background work continues.
  • Play — The owner obtains fresh, temporary playback access after the output is ready.
  • Recover — A retry reuses the accepted source and creates a new processing attempt. It does not require uploading the original video again.
What problem does FlickPond solve in one sentence?
It lets an application turn an owner’s uploaded video into a trackable, playable result through a reusable API, without building its own storage and encoding workflow.
Why does the upload response not wait for conversion?
Encoding takes longer than a normal interactive request. Durable acceptance and background processing let the client return promptly and check progress separately.

Level 2 / Explain the design

Why call this a platform?

A single website can process videos. A reusable platform also exposes that capability through a stable contract so another application can use it. FlickPond’s core capability is owner-scoped media intake, processing and output access. The browser and Publisher both consume that capability through HTTP. They do not need database passwords, queue credentials or copies of the encoding implementation.

In platform language, the processing capability is the seed. Content owners produce input videos. Applications consume the APIs and processed results. The useful claim is demonstrated reuse through a second client. It is not a claim that we built a commercial marketplace or proved adoption by external organizations.

Chapter 02

How the platform fits together

Follow the current Media and Processing design through its domain boundaries, durable hand-offs, worker path, and the trade-offs that keep the system understandable.

Media owns people, uploads, and playback access. Processing owns jobs and encoding attempts. They coordinate through versioned messages and each keeps its own database. A worker turns a pinned source version into outputs; Media then exposes those outputs only to the owner.

Level 1 / Understand the basics

Start with the work the system promises

Think of Flickpond as a place where an owner submits a video, asks for a transformation, and later watches the result. The visible item is an Asset: a video owned by one account, together with its source identity and edit operations. Its identifier is also the public job identifier, so clients can keep one reference from upload through status and playback.

Processing work has a different life from the Asset. One Asset can have one Processing Job, and that Job can have several numbered Attempts over time. A retry does not overwrite the first attempt; it creates a fresh attempt from the accepted source. This distinction makes it possible to explain which try failed, which one is current, and which output belongs to it.

Read all diagram notes
  • Owner — The account owns the Asset, source pin, public status, and right to play the outputs.
  • Job — Processing gives the accepted request a job identity and keeps its lifecycle.
  • Attempt — Each run has a unique number and identity; retries create another attempt.
Why are Job and Attempt separate?
A job describes the requested processing over time. An attempt records one execution. Keeping them separate means a retry can be new work without erasing the failure history or confusing old and new outputs.

Level 1 / Understand the basics

From client bytes to an accepted command

A browser or Publisher client first asks Media for an upload reservation. It sends a request key plus filename, declared content type, byte length, and SHA-256. Media validates the request and creates an owner-scoped reservation with a server-chosen S3 key. It returns a short-lived presigned POST. The client sends the bytes directly to S3, so a large video body does not travel through API Gateway or a Lambda function.

The client then calls finalize. Media verifies the uploaded object’s actual size, checksum, media type signature, and S3 VersionId. Verification happens outside SQL row locks because streaming bytes can take time. Media then locks the reservation and, in one database transaction, records the exact VersionId, creates the Asset, and stages a submit message. The accepted source is therefore not “whatever is currently at this key”; it is the immutable version Media checked.

Read all diagram notes
  • Reserve — Media fixes the key and expected file facts, then returns a short-lived upload grant.
  • Upload — The client transfers bytes to object storage without routing the video through the API.
  • Verify — Media checks stored bytes and records the S3 VersionId it actually verified.
  • Accept — One transaction adopts the Asset and records the command that will request processing.

This protocol has a cost: the client hashes the file before upload, and the system needs a versioned bucket plus cleanup for abandoned or late writes. That complexity buys a strong promise: the worker can later read the same bytes that Media accepted. A replay of an upload grant may create another object version, but the accepted source remains pinned to its original VersionId.

Idempotency makes uncertainty manageable. If a client repeats a reservation or finalization after a lost response, the request key lets Media return the already accepted item. Reusing the same key with different request data produces a conflict. This is especially important for Publisher: a transport timeout does not prove that the server failed to accept the file.

What if S3 has no object when finalize runs?
Media does not create an Asset or enqueue work. The missing upload is a recoverable client error, so the caller can retry or inspect the reservation without processing an unverified source.

Level 2 / Explain the design

Two owners, with a deliberate seam

The design has two bounded contexts: Media Management and Processing. Each has its own vocabulary, rules, database role, and code owner. Media owns accounts, ownership checks, upload reservations, pinned sources, public job reads, playback signing, deletion, and cleanup. Processing owns jobs, attempts, leases, retries, cancellation, output records, and encoder claims.

They use separate PostgreSQL databases and roles (media_db and processing_db) on one Aurora cluster. Each service can query its own tables and migration history. They do not join across databases or share ORM models. IDs crossing the seam are values in a contract, not foreign keys into the other service. This creates a clear ownership boundary, although the shared cluster remains a common capacity and failure boundary.

Media keeps a ProcessingProjection, a local read model of the latest accepted Processing state. A browser can ask Media for an owned Asset and its status in one domain. Media does not open a Processing database connection to answer that question. When a result arrives, Media validates it and updates its copy. Before the first result, Media can show accepted, a Media-side state that Processing does not emit.

Read all diagram notes
  • Media — Media decides who owns an Asset, which bytes are accepted, and whether a playback link may be issued.
  • Contracts — Versioned values describe actors, sources, and envelopes; they do not move database ownership.
  • Processing — Processing decides which attempt is current and whether a worker may claim or finish it.

Identity and playback stay with Media because those rules need the owner and Asset together. The user row, owner filter, source pin, and playback signer live in Media’s database. Splitting identity into a third service would make ordinary ownership and playback decisions depend on extra network calls, without creating a useful independent lifecycle. The architecture chooses two business services, not one service for every noun.

Is the Media authorizer a third service?
No. It is a separate execution role running Media code and reading Media’s user records. Service boundaries follow owned rules, data, and release units, not the number of deployed functions.

Level 2 / Explain the design

Messages carry work across the seam

Media and Processing do not call each other synchronously to create a job. Instead, Media’s transaction writes an outbox row beside the Asset change. A repair publisher later sends that row to the processing-commands queue. Processing consumes the command, records it in its inbox, creates its Job and Attempt, and stages a work message. A finite worker consumes processing-work. When state changes, Processing stages a result snapshot for the media-results queue; Media consumes it into the projection.

Why an outbox? A database commit and an SQS send cannot be one atomic operation. If the API changed SQL and then tried to send directly, a crash between the two could leave an accepted Asset with no command. With an outbox, the durable state change and intent-to-send commit together. A separate publisher can retry delivery. A claim token fences the publisher: after network I/O it acknowledges a row only if it still owns the claim.

Delivery is at least once, and Standard SQS can duplicate or reorder messages. The inbox stores a message ID and canonical body hash in the same transaction as the domain update. Repeating the same ID and body becomes a no-op; reusing an ID with different content is a conflict. Repair can reconstruct work from Processing’s SQL state if a queue entry is lost. These safeguards make the system recoverable; they do not make SQS exactly once.

Ordering is guarded at the domain level. Processing serializes submit, retry, and cancel with a per-Asset SubmissionGuard. Result snapshots carry increasing state_version values and attempt identity. Media ignores an older version, rejects conflicting content at the same version, and refuses an output outside the expected job/attempt path. An old worker may still finish a computation, but it cannot take authority from the current attempt.

Read all diagram notes
  • Commit — A state update and its message intent share one SQL transaction.
  • Publish — A publisher sends outside the SQL lock and acknowledges with a claim token.
  • Consume — The consumer deduplicates and commits domain state before queue acknowledgement.
  • Repair — A repair pass uses SQL as authority when transport delivery is missing or delayed.
Does inbox deduplication mean exactly-once processing?
No. It makes repeated delivery of a message ID and body harmless for the domain transaction. Delivery can still repeat, and repair is still needed for the SQL-to-queue gap.

Level 2 / Explain the design

From a worker lease to owner playback

The worker does not trust a queue message enough to start encoding. It asks Processing to claim the named Job and Attempt. Processing checks the source descriptor, owner and Asset identity, current-attempt status, submission guard, and finite task binding. If eligible, it creates a lease token and timestamps using the database clock. Heartbeats and finish operations must present that same live token before the deadline.

The worker downloads the pinned source, probes it, validates requested edits, and runs FFmpeg. Outputs live beneath jobs/{job_id}/attempts/{attempt_id}/. A successful attempt must report exactly one primary output; HLS is optional. Processing commits terminal state and result before the SQS work message is deleted. If a worker dies or loses its lease, its late completion is fenced out; the attempt becomes a visible failure/abandonment path and an owner retry creates a new Attempt.

When Media receives a result, it checks that the source matches its own accepted pin and that output keys belong to the stated attempt. It applies the state-version and attempt fences before updating ProcessingProjection. For MP4 playback, Media checks ownership and signs a short-lived S3 URL. For HLS, Media returns the playlist body and redirects segment requests to signed S3 locations. The playlist response is private and not cached. A foreign owner or unknown Asset appears not found.

Read all diagram notes
  • Claim — Processing grants one finite task temporary authority for the current attempt.
  • Encode — The worker reads the accepted version and writes namespaced outputs.
  • Project — Media accepts only a current, valid snapshot into its own read model.
  • Play — Media authorizes the owner and signs access to the completed output.

Failure example: suppose attempt 1 stalls, the owner retries, and attempt 2 starts. If the first worker wakes later and reports success, Processing’s lease/current-attempt checks prevent it from finishing as the authority. If a stale result nevertheless reaches Media through delayed delivery, the attempt number and state version prevent it from replacing attempt 2. The old output remains scoped under attempt 1 and is not the current playback result.

Why can a signed link expire?
The link is a short-lived capability to read one output. A fresh owner-authorized read can mint another; the system does not expose a permanent public object URL.

Level 3 / Defend the details

Know the boundaries and the trade-offs

This architecture limits coordination; it does not remove shared infrastructure. Media and Processing have separate databases and IAM roles, but they share one Aurora cluster. A database pause or cluster problem can affect both. Media can accept and durably hold a command while Processing is unavailable, but encoding waits for finite worker capacity. In the V1 operating path, a person starts bounded batches; an opt-in V2-live launcher can wake finite tasks up to its cap. Neither is an always-running encoder fleet.

The Publisher CLI is a separate integrator, not another business service. It uses the public HTTPS API and has no application, database, or storage imports. That boundary lets another team automate folder publishing without receiving service credentials. The public contract is documented in the current OpenAPI files; contracts/ serves as the shared message language between service images.

Keep the historical distinction clear in a presentation. Root-level app/ and app/worker/ contain an earlier monolithic runtime and are useful as history, but the current AWS-oriented V1 paths are media/, processing/, contracts/, delivery/, and runtime_support/. Some current files even say that behavior was extracted from app, such as media/api/v1_hls.py. Do not describe the old app worker or Redis/RQ as the active V1 path. The current design records SQS plus SQL outbox/inbox and finite workers.

A useful design test is: does this abstraction protect a real invariant, boundary, or repeated policy? Repositories centralize owner-filtered SQL reads; application services compose business actions; adapters contain storage and transport behavior; contracts define cross-boundary values. More layers would not automatically help. A pass-through wrapper used once, another service for every feature, or a generic workflow engine would increase navigation and release coordination without protecting a rule.

AWS: a small cloud, with clear boundaries

Follow one upload through the live V2 AWS system. Learn what each service owns, how work moves, and where the current design still has limits.

The browser reaches our application through CloudFront and an HTTP API. Separate Media and Processing Lambda applications own their own data and queues. Video bytes go straight to private S3, while finite Fargate workers encode them. A bounded Lambda launcher starts those workers when work is waiting.

Level 1 / Understand the basics

Start with the shape of the system

Think of the project as two business services with a shared delivery path. Media owns people, assets, upload reservations, source ownership and playback grants. Level 1 / Understand the basics

Follow the bytes separately from the requests

A video upload is large, so it does not travel through API Gateway or a Lambda request body. The browser asks Media to reserve an owner-scoped S3 key. Level 2 / Explain the design

Two databases, one shared Aurora cluster

Media and Processing each have a separate PostgreSQL database on one Aurora PostgreSQL Serverless v2 cluster. Each has its own runtime and migration credentials, schema history and owner application. Media's role cannot read Processing's database, and Processing does not borrow Media credentials. The services exchange versioned messages and identifiers rather than running cross-domain SQL.

The cluster is shared infrastructure, though. It is a common capacity and failure boundary, and activity for either database can keep it awake. Later, after the #273 backoff change, the accepted release recorded 0.0 ACU at 18:07 UTC on 19 October, about 56 minutes after the last upload. Level 2 / Explain the design

Messages coordinate work; SQL remains the record

The deployed system uses three standard SQS queues: Processing commands, Processing work and Media results. Each has a matching dead-letter queue for messages that exceed their retry policy. Messages carry identifiers and versioned facts, not the video itself, secrets or expiring presigned POST URLs and fields.

The important reliability pattern is an outbox. A service commits its business change and the message intent together in its own SQL transaction. A later publisher sends the queued intent. The receiving service records and deduplicates the message with its own state before acknowledging it. If a send or acknowledgement response is lost, retry and duplicate delivery are expected; the durable state and message IDs make recovery possible. SQL and SQS are not one atomic transaction, so repair code and monitoring still matter.

  • Wake — An immediate Lambda wake and a scheduled safety tick inspect SQL, queue depth, and ECS task state.
  • RunTask — The launcher reserves a slot and asks ECS to start a task with a bounded deadline and unique identity.

Level 2 / Explain the design

Why Lambda coordinates and Fargate encodes

Lambda fits short, event-driven work: API requests, message handlers, repair passes and the launcher. AWS starts an invocation when needed, and the function ends when its bounded handler finishes. Fargate fits the existing FFmpeg pipeline: a task can hold more CPU and memory, download source data, encode multiple outputs, upload them, and stop when its one job is done.

The live worker task is 2 vCPU and 4 GiB, with one active encode. The launcher counts running, stopping and unresolved launches against a cap of three. It records a reservation before calling ECS; if a response is ambiguous, the next pass checks task identity or replays the same token and payload. This keeps concurrent launch attempts from casually exceeding the cap. Each task gets a finite lifetime and an absolute deadline, so an empty or stuck worker does not become a resident service.

Level 2 / Explain the design

Subnet choices and the egress tradeoff

The current rendered V1 foundation places Lambda and Aurora in private, dual-stack subnets across two availability zones. The design has no NAT Gateway, paid interface endpoints, application EC2 host, load balancer or Redis service. Lambda uses IPv6 egress-only routing for AWS service APIs such as SQS, Systems Manager Parameter Store and ECS, plus an S3 gateway endpoint. The gateway path also permits the required regional container-image layer download path.

Fargate workers and migration tasks use public subnets with temporary public IPv4 while they run. Narrow security groups allow their database connection into Aurora; the database itself stays private. Public task placement makes image pulls and secret retrieval possible without a NAT Gateway, but it means those tasks have public egress and a temporary public address. Security groups, IAM and TLS still matter. Do not say every compute component is in a private subnet.

Level 2 / Explain the design

Transactions make the promise precise

The most instructive function is direct_intake.finalize. It first looks up the reservation by both reservation ID and owner ID, checks that the request ID matches, and returns the existing Asset on replay. It then leaves the SQL transaction before calling storage.verify_direct_upload. The storage call can perform HEAD plus a bounded streaming GET; holding a row lock while waiting on network I/O would lengthen contention and increase the chance that an unrelated request stalls.

After verification returns the exact S3 VersionId, finalize opens a new transaction and locks the reservation. It rechecks whether another request finalized it or whether it expired during verification. If still valid, it records the VersionId and creates the Asset. Finally it stages the submit message before the same transaction commits. The important boundary is not “database versus storage” in general; it is: slow remote byte inspection outside the lock, then one short local commit that adopts verified bytes and records the intent to process them.

media/repositories/assets.py:fingerprint computes a stable SHA-256 of canonical JSON, and replay uses the (owner, operation, key) identity to make a repeat safe. If the key exists with a different request hash, it raises a conflict. Idempotency is a persisted rule, not an HTTP retry trick. It lets the browser or Publisher recover from a lost response without accidentally creating a second Asset.

SQL join choices should reflect ownership. list_asset_pages uses an outer join between Asset and ProcessingProjection. That join is appropriate because both tables live in Media’s database and the projection may not exist yet. If Media reached into Processing’s database for every status page, it would couple availability, permissions, and query latency across a service boundary. The projection duplicates a small amount of state to keep the public read local.

Level 2 / Explain the design

The failure between saving and sending

Suppose Media saves an accepted asset, then crashes before sending its processing command to SQS. Without a durable record of the intended message, the asset could remain accepted forever without any work. Reversing the order is also unsafe: the queue could receive work for a database transaction that later rolls back.

Read all diagram notes
  • One transaction — The local SQL commit records the business change and its message intention together. Either both commit or neither does.
  • Publish later — A publisher claims a due row, sends outside the database lock, then records the outcome. Lost replies can cause another send.
  • Accept once — The consumer checks message identity, updates its own state and stages resulting messages in a transaction before acknowledging delivery.

The inbox records a message ID and body hash. Repeating the same ID and meaning can be recognized; reusing the ID for different content is a conflict. Outbox publication has its own claim token so an obsolete publisher cannot casually overwrite a later publisher’s outcome. SQL row locking and uniqueness constraints support these decisions under concurrency.

Why is an outbox needed if SQS is already durable?

Level 2 / Explain the design

Why a worker needs a lease

Starting a container is not permission to finish any job it chooses. A worker claims a current attempt and receives a time-limited lease token. Heartbeats extend its authority while it remains healthy. The database clock, current attempt and token determine whether a finish operation is valid.

Imagine worker A stalls. Recovery marks its attempt no longer live and allows later work. If A eventually wakes and uploads output, it must not replace the result of worker B. A fence checks that A still owns the current attempt and lease before accepting completion. Attempt-specific output paths also stop one attempt from overwriting another’s namespace.

Who can do what, and why?

Level 1 / Understand the basics

Media hashes account passwords with bcrypt and issues a signed JSON Web Token in an access_token cookie. The cookie is Secure, HttpOnly and SameSite=Strict. In plain terms, it is sent over HTTPS, withheld from ordinary browser JavaScript, and restricted in cross-site contexts. Those controls reduce risks; they do not replace endpoint authorization.

The Media-owned authorizer verifies the token and reads the current user record. Processing receives the resulting actor identity, not Media’s JWT signing secret or a copy of its users table. It still checks ownership of its own jobs. The design therefore has a real dependency: if Media’s authorizer or account lookup is unavailable, protected Processing requests cannot simply bypass authentication.

Is authentication enough to stop one user reading another user’s video?
No. Authentication identifies the caller. Every protected resource operation also needs an ownership check. A logged-in Arun must still be denied access to Maya’s asset or job.
